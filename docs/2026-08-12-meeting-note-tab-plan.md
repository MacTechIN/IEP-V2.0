## 무엇을 하는가

세 가지다.

1. **탭 재배치** — `미팅노트 / 리포트 / 지표` 순. 지금 리포트 탭 맨 위에 있는 **미팅 노트**를 통째로 미팅노트 탭으로 옮긴다. 그러면 `AI 요약` 이하가 리포트 탭 맨 위로 올라온다.
   (녹취는 리포트 탭이 아니라 별도 `녹취` 탭에 있다 — 그것도 함께 미팅노트 탭으로 들어온다)
2. **미팅노트 탭을 좌우로 분할** — 왼쪽 녹취, 오른쪽 미팅노트 , 모바일 환경은은 위(미팅노트)아래(녹취)로 자동으로 변경(모바일ui 자동배치)  
 **기존** `녹취` **탭은 없앤다** (이 안으로 완전히 들어온다).
3. **녹취 편집** — 잘못 전사된 부분을 직접 고치고, 복사하고, 형광펜으로 표시한다.
 수정하면 **미팅노트와 AI요약만** 다시 만든다. 네이버 클로바노트 의 기능을 그대로 벤치마킹한다. (기타 기능도 더 벤치마킹해도 좋다)

## 추가 요구사항 검토 (2026-08-12 사용자 보완)

계획서에 네 가지가 추가됐다. 각각 **가능한가 · 얼마나 드는가 · 어느 차수인가**를 따진다.

### ① 모바일은 미팅노트가 위, 녹취가 아래

데스크톱은 `녹취 | 미팅노트`(좌우)인데 모바일은 `미팅노트 / 녹취`(위아래)다.
**단순히 쌓는 것이 아니라 순서가 뒤집힌다.**

가능하다. CSS 로 해결된다 — 마크업에서 미팅노트를 먼저 두고, 데스크톱에서만
`flexDirection: 'row-reverse'` 로 좌우를 바꾼다. 자바스크립트 분기가 필요 없다.

> **왜 이 순서가 맞나**: 모바일에서 먼저 보고 싶은 것은 정리된 결과다.
> 녹취를 위에 두면 수백 줄을 스크롤해야 미팅노트에 닿는다.

**1차에 포함.** 추가 비용 없음.

### ② 형광펜을 단어 단위로

드래그가 글자 중간에서 끝나도 **단어 경계까지 넓혀서** 칠한다.

가능하다. 브라우저의 `Selection` 을 받아 앞뒤로 공백·문장부호를 만날 때까지 확장한다.
한국어는 띄어쓰기가 단어 경계와 정확히 맞지 않지만(조사가 붙는다),
**어절 단위로만 맞춰도 "글자 중간에서 잘린" 어색함은 사라진다.**

형태소 분석까지 하면 `-은/는/이/가` 를 떼어낼 수 있지만, 라이브러리가 무겁고
칠하는 범위가 사용자 예상과 어긋날 수 있다. **어절 단위로 한다.**

**2차-c 에 포함.** 추가 비용 없음.

### ③ 녹취 커서 위치에 맞춰 미팅노트가 따라 스크롤

**이것이 이번 추가분에서 가장 무겁다.** 그런데 공짜로 푸는 길이 있다.

문제: `MeetingNote.topics` 에는 **시간도 세그먼트 참조도 없다.**
`{title, points[]}` 뿐이다. 그대로는 "지금 보는 녹취 줄"과 "노트의 어느 주제"를 이을 수 없다.

세 가지 안:

| 안 | 정확도 | 비용 |
|---|---|---|
| 비율로 맞추기 — 녹취 40% 지점 → 노트 40% 지점 | 낮음 | 0 |
| **구간 번호를 기록해 두기 (채택)** | 중간 | **0** |
| LLM 에게 주제마다 시간대를 내놓게 하기 | 높음 | 프롬프트 변경 + 품질 위험 |

**채택안이 공짜인 이유**: `generateMeetingNote` 는 이미 녹취를 12,000자 창으로 나눠
각각 요약하고, `topics: partial.flatMap((p) => p.topics)` 로 **순서를 살려 이어붙인다**(openai.ts:517).
즉 **주제는 이미 녹취 순서대로 배열돼 있다.** 각 주제가 몇 번째 창에서 나왔는지만
함께 담으면, 창 → 글자 범위 → 세그먼트로 되짚을 수 있다.

```ts
// MeetingNote.topics 에 필드 하나 추가 (기존 필드는 그대로)
topics: { title: string; points: string[]; part?: number }[]
```

`part` 가 없는 옛 노트는 **비율 방식으로 자동 폴백**한다. 다시 분석할 필요가 없다.

> 정확도는 "중간" 이다. 12,000자 창은 대략 8~10분 분량이라 그 안에서는 못 짚는다.
> **보조 기능이라고 하셨으니 이 정도면 맞다** — 더 정밀하게 하려면 LLM 을 건드려야 한다.

**2차에 포함** (노트 재생성 시점에 `part` 가 채워진다). 스크롤 연동 자체는 화면 작업이다.

### ④ 수정 이력을 화면에서 어떻게 보여줄까 — 추천

요청: "색상이나 밑줄로 변경 포인트를 표시하고, 동일한 번호로 링크"

세 가지를 검토했다.

| 안 | 어떻게 보이나 | 문제 |
|---|---|---|
| 인라인 표시만 | 고친 줄에 왼쪽 색 테두리 + `수정됨` 뱃지 | 어디를 고쳤는지 찾으려면 전부 훑어야 한다 |
| **번호 + 이동 (추천)** | 고친 줄에 `①②③`, 상단에 `수정한 곳 3` 칩 → 누르면 다음 수정 지점으로 이동 | 없음 |
| 원문 대조 보기 | 취소선 원문과 수정본을 나란히 | 녹취가 두 배로 길어져 읽기 어려워진다 |

**추천: 번호 + 이동.**

- 고친 줄은 **왼쪽 테두리 색 + 옅은 배경**, 번호는 작은 위첨자 `①`
- 상단 `수정한 곳 3` 을 누르면 ①→②→③ 순으로 스크롤하며 순회
- 번호에 마우스를 올리면 **원문이 툴팁**으로 (되돌리기 버튼 함께)
- 재요약 후에도 번호는 유지된다 — 번호는 노트가 아니라 **녹취**에 붙는 것이다

> 밑줄은 쓰지 않는다. 형광펜과 헷갈린다 — 둘 다 "글자에 뭔가 그어진" 것으로 보인다.
> **수정은 줄 전체(테두리), 형광펜은 글자 범위(배경색)** 로 층을 나눈다.

**2차-c 에 포함.**

### ⑤ 클로바노트 벤치마킹 — 무엇을 가져오고 무엇을 안 가져오나

| 클로바노트 기능 | 이번에 | 이유 |
|---|---|---|
| 좌우 분할 (녹취 / 메모·요약) | **가져온다** | 이번 작업의 핵심 |
| 녹취 인라인 수정 | **가져온다** | 요청 사항 |
| 형광펜 | **가져온다** | 요청 사항 |
| 복사 버튼 | **가져온다** | 요청 사항 |
| 핵심 키워드 칩 | **가져온다** | 이미 있는 `mentions` 를 올려 쓰면 된다. 추가 비용 0 |
| 구간별 요약 (`00:00~01:25 미군의 오폭 사고`) | **안 가져온다** | 새 LLM 기능. 별도 건으로 |
| 오디오 재생·구간 이동 | **안 가져온다** | 저장된 오디오를 돌려주는 라우트가 아직 없다 |
| 화자 이름 일괄 변경 | **안 가져온다** | 범위 밖 |

핵심 키워드 칩만 새로 넣는다 — **공짜이기 때문**이다.

### 구현 방식

- `tab` 상태의 타입에 `'note'` 추가, 초기값을 `'note'` 로
- 미팅 노트 렌더링 블록(현재 246~300행)을 **잘라내서** 새 탭으로 이동 — 내용은 한 글자도 안 바꾼다
- 녹취 렌더링 블록(709행~)도 **잘라내서** 좌측 컬럼으로 이동
- 좌우 분할은 MUI `Grid` — `xs=12`(모바일 위아래) / `md=6`(데스크톱 좌우)
- **마크업 순서는 미팅노트 → 녹취.** 데스크톱에서만 `row-reverse` 로 좌우를 뒤집는다.
  그래야 모바일에서 미팅노트가 위로 온다 (요구사항 ①)
- 각 컬럼에 `maxHeight` + `overflowY: auto` — 한쪽이 길어도 다른 쪽이 밀리지 않는다
- **핵심 키워드 칩**을 미팅노트 맨 위에 — 이미 있는 `mentions` 를 올려 쓴다 (LLM 추가 호출 없음)

### 건드리지 않는 것

- 화자 필터 · 검색 · 맞장구 접기(`SHORT_CHARS = 10`) — **그대로 옮긴다**
- 리포트 탭의 나머지 전부 (AI요약, 관심사, 우려, 후속조치, 스코어, 코칭, 스코어카드…)
- 지표 탭 전부
- 3초 폴링, `isResult` 판정, 액션아이템 체크
- API · DB · Worker — **한 줄도 안 바꾼다**

### 검증

- `npx tsc --noEmit`
- 실제 미팅으로 3탭 전환 확인
- **리포트 탭에서 미팅노트만 빠지고 나머지가 순서·내용 그대로인지 대조**
- 모바일 폭에서 **미팅노트가 위, 녹취가 아래**로 쌓이는지 (단순 쌓기가 아니라 순서가 뒤집힌다)

**되돌리기**: 한 파일 되돌리고 재배포. DB 변경이 없어 흔적이 남지 않는다.

## 2차 — 녹취 편집 · 형광펜 · 재요약

### 마이그레이션 `011`

```sql
alter table v2.transcript_segments
  add column if not exists content_original text,   -- AI 가 처음 뽑은 원문
  add column if not exists edited_at timestamptz,
  add column if not exists edited_by uuid references v2.users(id),
  add column if not exists highlights jsonb default '[]'::jsonb;
  -- highlights: [{start:12, end:30}] — content 기준 문자 오프셋.
  -- 저장은 문자 오프셋이지만 **칠할 때 어절 경계로 넓힌다** (요구사항 ②)

alter table v2.meetings
  add column if not exists transcript_edited_at timestamptz,   -- 마지막 녹취 수정
  add column if not exists note_generated_at timestamptz;      -- 마지막 재요약
  -- 둘을 비교해 "요약이 낡았다" 를 판정한다. 플래그를 따로 두면 어긋난다.
```

**`content_original` 은 처음 수정할 때만 채운다.** 이미 값이 있으면 덮지 않는다 —
두 번째 수정에서 덮으면 "AI 원문" 이 아니라 "직전 내 수정본" 이 되어 되돌리기가 무의미해진다.

### API 3개 추가


| 엔드포인트                                               | 하는 일                                 |
| --------------------------------------------------- | ------------------------------------ |
| `PATCH /analysis/meeting/:id/segments/:segId`       | 한 세그먼트의 `content` 또는 `highlights` 수정 |
| `POST /analysis/meeting/:id/renote`                 | 미팅노트 + AI요약만 재생성                     |
| `POST /analysis/meeting/:id/segments/:segId/revert` | 원문으로 되돌리기                            |


**기존 엔드포인트는 손대지 않는다.** 전부 새 경로다.

### 재요약이 무엇을 바꾸나

```
바꾼다:   analysis_results.meeting_note   ← topics[].part 가 여기서 채워진다
          analysis_results.summary
          meetings.note_generated_at

안 바꾼다: interests · concerns · action_items · action_items_done
          follow_up_draft · scores · talk_metrics · speaker_roles
          psych_insights · coaching · scorecard · sentiment
          transcript_segments (재요약은 녹취를 다시 쓰지 않는다)
```

`**action_items_done` 을 지키는 것이 특히 중요하다** — 사용자가 체크한 후속 조치다.
0030 에서 재분석이 이걸 날리던 것을 고쳤는데, 여기서 되살리면 안 된다.

### 화면 동작

1. 녹취 한 줄에 마우스를 올리면 **연필·복사** 아이콘
2. 연필 → 그 줄만 입력창으로. `Esc` 취소, `Ctrl+Enter` 또는 바깥 클릭으로 저장
3. 저장하면 그 줄에 **수정됨** 표시 + 원문 보기(툴팁)
4. 드래그하면 **형광펜** 버튼 → 칠하기 / 지우기
5. 하나라도 수정되면 오른쪽 미팅노트 위에 배너:
 **"녹취가 수정되었습니다 — 미팅노트와 AI요약 갱신하기"**
6. 누르면 3~8초 뒤 갱신. 그동안 버튼은 비활성 + 진행 표시

### 왜 "버튼" 인가 (다른 안과 비교)


| 안           | 장점                   | 문제                                                        |
| ----------- | -------------------- | --------------------------------------------------------- |
| 저장할 때마다 자동  | 손이 덜 감               | 한 줄 고칠 때마다 LLM 호출. 열 줄 고치면 열 번. 화면이 계속 바뀌어 어디를 보던 중인지 잃는다 |
| 30초 디바운스    | 호출이 묶임               | **언제 도는지 예측이 안 된다.** 더 고치려던 중에 돌고, 다 고쳤는데 안 돌기도           |
| **버튼 (채택)** | 호출 1회 · 시점을 사용자가 압니다 | 한 번 더 눌러야 함                                               |


여러 곳을 고치고 한 번에 갱신하는 것이 실제 사용 흐름에 맞고, 비용도 최소다.

### 검증

- 마이그레이션을 Docker Postgres 에서 0001~011 전체 적용
- **`content_original` 이 두 번째 수정에서 덮이지 않는지** (회귀 테스트)
- 재요약 후 `action_items_done` 이 보존되는지 — **0030 회귀 방지**
- 재요약이 리포트·지표·코칭을 바꾸지 않는지 (전후 컬럼 대조)
- 남의 미팅 세그먼트를 수정할 수 없는지 (조직 범위)
- **형광펜이 어절 경계로 넓혀지는지** (글자 중간 드래그 → 어절 전체)
- **`part` 없는 옛 노트에서 스크롤이 비율 폴백으로 동작하는지** (재분석 없이)
- `tests/25_transcript_edit.sql` 로 남긴다

## 위험과 대비


| 위험                   | 대비                                              |
| -------------------- | ----------------------------------------------- |
| **기존 기능이 깨진다**       | 1차는 DB 무변경 · 한 파일. 2차는 전부 새 엔드포인트·새 컬럼          |
| 재요약이 다른 결과를 덮는다      | 갱신 대상 컬럼을 명시적으로 지정. 회귀 테스트로 확인                  |
| 형광펜 오프셋이 수정으로 어긋남    | **수정하면 그 줄의 형광펜은 지운다.** 위치를 추적하려 들면 반드시 틀어진다    |
| 두 사람이 같은 줄을 동시 수정    | `updated_at` 비교로 나중 것이 이김. 지금 사용 규모에서는 실질 위험 없음 |
| 긴 녹취(300줄+)에서 편집이 느림 | 줄 단위 렌더링 유지. 전체 리렌더가 아니라 그 줄만                   |
| 재요약 실패               | 실패해도 기존 미팅노트를 지우지 않는다. 오류만 표시                   |
| 스크롤 동기화가 어긋나 보인다     | 창이 8~10분 단위라 그 안에서는 못 짚는다. **보조 기능임을 화면에서 드러낸다**(부드럽게 따라가되 강제 이동은 안 함) |
| 형광펜 어절 확장이 과하게 잡힌다   | 한국어 조사까지 딸려온다. 형태소 분석은 하지 않는다 — 무겁고 예상과 더 어긋난다 |
