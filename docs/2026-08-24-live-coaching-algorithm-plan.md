# 실시간 코칭을 우리 알고리즘으로 — 개발 기획

- 작성일: 2026-08-24
- 코드 기준: `v2.15.0`
- 해부도: `docs/2026-08-24-live-coaching-pipeline.html`
- 상태: **기획. 착수 전.** 아래 「정해 주셔야 하는 것」이 먼저다

---

## 0. 결론부터

지금 코칭은 **프롬프트 한 장**이다. 25초 전사문을 `gpt-4o-mini` 에 넣고
`{level, reason, script, action}` 을 받는다. 그 위에 클라이언트가 위험 2연속 규칙 하나를 얹는다.

**이걸 "우리 알고리즘" 으로 바꾸는 데 가장 먼저 필요한 것은 모델이 아니다. 기록이다.**

> 지금은 판정이 맞았는지 틀렸는지 **알 방법이 없다.**
> 클립도, 전사문도, 판정 결과도 응답으로 한 번 나가고 사라진다.
> 재지 못하면 고칠 수 없고, 고칠 수 없으면 그건 우리 것이 아니라 OpenAI 것이다.

프롬프트를 아무리 정교하게 고쳐도 **좋아졌는지 말할 수 없다.** 그래서 1단계는 프롬프트가 아니라
저장이다. 이 판단은 8/20~8/24 에 반복해서 확인한 것과 같다 — 재는 장치가 없으면 고쳤다는 말이
증명되지 않는다.

## 1. 지금 무엇이 도는가

```
브라우저 ─25초 클립──▶ POST /api/v2/risk
                        ├─ whisper-1        전사 (화자 없음)
                        └─ gpt-4o-mini      판정 (temp 0.3, JSON 강제)
                     ◀── {level, reason, script, action, transcript}
클라이언트: danger 2연속일 때만 위험으로 승격, 아니면 주의로 완충
```

| | 값 | 어디 |
|---|---|---|
| 주기 | 25초 (응답 뒤 다음 주기 — 꼬리물기) | `UploadPage.tsx` `RISK_INTERVAL_MS` |
| 전사 | `whisper-1` | `services/risk.ts` `transcribeQuick` |
| 판정 | `gpt-4o-mini`, `temperature 0.3`, `max_tokens 500` | `services/risk.ts` `assessRisk` |
| 입력 문맥 | 이번 25초 + 직전 주기 전사문 | `form.append('context', …)` |
| 등급 | `normal` · `caution` · `danger` · `opportunity` | 프롬프트 |
| 저장 | **없음** (설계 의도) | `risk.ts` 머리주석 |
| 호출량 | 1시간 = **288회** (STT 144 + 판정 144) | 실측 계산 |

**2026-08-24 부터 기본이 켜짐이다.** 그전에는 대부분의 회의에서 아예 돌지 않았다.
비용도 데이터도 **이제부터** 실제로 쌓인다 — 기획을 지금 세우는 이유가 이것이다.

## 2. 무엇이 없는가

### ① 판정이 남지 않는다 ← **나머지 전부의 선행 조건**

`risk.ts` 머리주석이 자랑스럽게 적고 있다 — "파일을 보관하지 않는 유일한 업로드 경로".
오디오를 안 남기는 것은 옳다. **그런데 판정 결과까지 함께 사라지는 것은 의도가 아니라 부작용이다.**

그래서 지금 답할 수 없는 질문들:

- 어제 회의에서 주의가 몇 번 떴나? 그중 몇 개가 맞았나?
- 프롬프트를 고쳤는데 나아졌나?
- 위험 2연속 규칙이 실제로 오탐을 줄이고 있나, 진짜 위험을 놓치고 있나?
- 계약된 미팅과 실패한 미팅에서 신호가 다른가?

### ② 화자를 모른다

`whisper-1` 은 화자 분리를 하지 않는다. 화면 예시의
*"상대방의 마음속에 의구심이 있는 것으로 보임"* 은 **누가 말했는지 모르는 상태에서 나온 추론**이다.
영업담당 본인의 걱정을 고객의 저항으로 읽을 수 있고, 그 반대도 된다.

### ③ 문맥이 25초 + 직전 한 덩이뿐

**이미 DB 에 있는데 안 쓰는 것들:** 미팅 제목, 사전 메모(`meetings.notes`),
고객사, 그 고객사의 지난 미팅 요약·점수·액션아이템.
사후 분석(`AnalysisWorkflow`)은 이것들을 쓴다. 실시간만 안 쓴다.

### ④ 코드로 셀 수 있는 것을 모델에게 묻는다

발화 점유율, 침묵 길이, 말 끊김, 속도 변화, 질문 비율 — **계산하면 되는 값**이다.
사후에는 `computeTalkMetrics` 가 이미 코드로 센다. 실시간에는 없다.
LLM 에게 세게 하면 비싸고, 느리고, 매번 답이 흔들린다.

### ⑤ 모두에게 같은 기준

사람마다 말 속도·질문 습관·목소리 톤이 다르다. 기준선이 없으니
**"평소와 다르다" 를 말할 수 없다.** 원래 말이 빠른 사람과 지금 빨라진 사람을 구분 못 한다.

### ⑥ 성과와 이어지지 않는다

코칭이 계약에 도움이 됐는지 볼 고리가 없다. **검증되지 않은 코칭은 조언이 아니라 소음이다.**

## 3. 무엇을 만들 것인가 — 네 겹

우리 알고리즘은 "더 좋은 프롬프트" 가 아니라 **네 겹이 쌓인 것**이다.
아래로 갈수록 우리 것이고, 위로 갈수록 남의 것이다.

```
  4  보정 · 개인화     ← 우리 데이터가 있어야만 가능
  3  규칙 + LLM 합의   ← 우리 판단이 들어가는 자리
  2  신호 (코드 계산)   ← 값싸고 결정적이고 흔들리지 않는다
  1  기록              ← 없으면 위 셋이 전부 추측이다
```

### 1겹 — 기록 (선행 조건)

**오디오는 계속 저장하지 않는다.** 남기는 것은 세 가지다.

| 남길 것 | 왜 |
|---|---|
| 판정 결과 (`level`·`reason`·`script`·`action`) | 나중에 맞았는지 보려면 |
| 그 주기의 전사문 | 왜 그렇게 판정했는지 되짚으려면 |
| 계산된 신호값 (2겹) | 모델 없이도 다시 계산·검증 가능하게 |

여기에 **사람의 응답**을 붙인다 — 카드에 `도움됨 / 빗나감` 두 개.
이것이 유일한 정답표(ground truth)다. 없으면 4겹이 영원히 불가능하다.

### 2겹 — 신호 (코드로 계산)

LLM 없이, 서버에서, 결정적으로 계산되는 값들. 실시간 자막(Deepgram)이 **화자 번호와 단어 시각**을
이미 주고 있어 대부분 공짜다.

- **발화 점유율** — 최근 2분간 영업담당 vs 고객 비율, 그리고 그 **변화율**
- **침묵** — 2초 이상 공백의 횟수·최장 길이
- **말 끊김** — 상대 발화 종료 전 시작한 횟수
- **질문 비율** — 영업담당 발화 중 물음의 비중
- **속도** — WPM, 그리고 **그 사람의 기준선 대비** 편차
- **어휘 신호** — 가격·계약·경쟁사·일정 관련 표현의 등장

**대부분 사후 분석에 이미 있다.** `computeTalkMetrics` 를 실시간에서도 쓸 수 있게 떼어내는 일이지
새로 발명하는 일이 아니다.

### 3겹 — 규칙 + LLM 합의

지금은 LLM 혼자 결정한다. 바꿀 모양:

```
신호(2겹)   ──▶ 규칙 판정 ──┐
                            ├──▶ 합의 ──▶ 최종 등급 + 근거
전사문      ──▶ LLM 판정 ──┘
```

- **둘이 일치하면** 그대로, 신뢰도 높음
- **규칙만 경보하면** 낮은 등급으로 (예: 침묵이 길지만 말은 평온함)
- **LLM만 경보하면** 낮은 등급으로 (지금의 오탐 대부분이 여기)
- **둘 다 조용하면** 정상

핵심은 **근거를 사람 말로 남기는 것**이다.
지금: *"상대방의 마음속에 의구심이 있는 것으로 보임"* (출처 불명)
바꾼 뒤: *"고객 발화가 최근 2분간 42% → 11% 로 줄었고 가격 언급 뒤 8초 침묵이 두 번"* (검증 가능)

### 4겹 — 보정 · 개인화

1~3겹이 3개월쯤 쌓인 뒤에 가능하다.

- **개인 기준선** — 이 영업담당의 평소 속도·질문 비율. 편차로 판정
- **임계값 보정** — 실제 `도움됨/빗나감` 비율로 등급 경계를 조정
- **성과 연결** — 계약된 미팅과 실패한 미팅의 신호 패턴 차이
- **고객사 이력** — 이 고객이 지난번에 무엇에 저항했는지

## 4. 개발 시점에 추가해야 할 것 (구체)

### 마이그레이션 `015` — 코칭 기록

```sql
create table if not exists v2.coaching_events (
  id             uuid primary key default gen_random_uuid(),
  user_id        uuid not null references v2.users(id) on delete cascade,
  -- 녹음 시작 시점에 만들어지는 값. 미팅은 나중에 붙는다(붙지 않을 수도 있다).
  session_id     text not null,
  meeting_id     uuid references v2.meetings(id) on delete set null,
  at_ms          integer not null,      -- 녹음 시작 기준 경과
  level          text not null,         -- 모델이 준 원본 등급
  level_shown    text not null,         -- 화면에 실제로 뜬 등급 (완충 적용 후)
  reason         text,
  script         text,
  action         text,
  transcript     text,                  -- 그 주기 전사문
  signals        jsonb,                 -- 2겹 계산값
  feedback       text,                  -- 'helpful' | 'missed' | null
  feedback_at    timestamptz,
  created_at     timestamptz not null default now()
);
create index on v2.coaching_events (user_id, created_at desc);
create index on v2.coaching_events (meeting_id) where meeting_id is not null;
```

**`level` 과 `level_shown` 을 따로 두는 것이 요점이다.** 완충 규칙이 실제로 도움이 되는지
재려면 "모델은 뭐라 했나" 와 "사람은 뭘 봤나" 가 둘 다 있어야 한다.

**`session_id` 로 먼저 쌓고 미팅은 나중에 붙인다.** 코칭은 미팅이 만들어지기 전에 돌기 때문이다 —
녹음 구간이 `meeting_id` 없이 먼저 올라가는 것과 같은 구조다(2.10.0).
미팅을 만들 때 같은 `session_id` 의 이벤트에 `meeting_id` 를 채운다.

### API

| 경로 | 무엇 |
|---|---|
| `POST /api/v2/risk` (수정) | `sessionId`·`atMs` 를 받고, 판정 뒤 `coaching_events` 에 남긴다. 응답에 `eventId` 추가 |
| `PATCH /api/v2/coaching/:id/feedback` (신규) | `helpful` \| `missed`. 소유자만 |
| `GET /api/v2/coaching/meeting/:id` (신규) | 그 미팅의 코칭 타임라인 — 사후 리포트에 얹는다 |

### 화면

- 코칭 카드에 **`도움됐어요 / 빗나갔어요`** 두 버튼. 누르면 사라지고 다음 카드로
  — **한 번에 두 글자 이상 요구하지 않는다.** 회의 중이다
- 미팅 상세에 **코칭 타임라인** — 언제 무엇이 떴고 무엇을 눌렀는지
- 관리자 화면에 **주간 집계** — 등급별 건수, 피드백 비율, 오탐률

### 서버 계산 (2겹)

`worker/src/services/signals.ts` 를 새로 만들고,
`computeTalkMetrics`(현재 `workflows/analysis.ts` 안)를 거기로 옮겨 **실시간과 사후가 같은 함수**를
쓰게 한다. 두 곳에서 따로 세면 숫자가 갈라지고, 갈라지면 어느 쪽을 믿을지 알 수 없다.

실시간 신호의 입력은 **Deepgram 이 이미 주고 있는 것**을 쓴다 — 화자 번호와 단어 시각.
지금은 화면에 뿌리고 버린다.

### 프롬프트

- 미팅 제목·사전 메모·고객사명·직전 미팅 요약을 `system` 에 넣는다 (이미 DB 에 있다)
- 2겹 신호값을 **숫자 그대로** 넣고, 모델에게는 **해석만** 시킨다
- `reason` 에 **근거가 된 신호를 명시**하게 한다 — 검증 가능한 문장을 요구하는 것이다

## 5. 순서

| 단계 | 무엇 | 왜 이 순서인가 |
|---|---|---|
| **1** | 마이그레이션 `015` + `/risk` 가 기록 + 카드에 피드백 두 버튼 | **이것이 없으면 2단계 이후를 잴 수 없다** |
| **2** | 2~4주 그냥 모은다. 아무것도 안 고친다 | 기준선이 있어야 개선을 증명한다 |
| **3** | `signals.ts` — 신호 계산을 실시간에 도입, 기록에 함께 남긴다 | 아직 판정은 안 바꾼다. **관측만** |
| **4** | 규칙+LLM 합의로 판정 교체 | 이때 1~3단계 데이터로 **전후 비교** |
| **5** | 개인 기준선·임계값 보정 | 데이터가 충분해진 뒤 |

**2단계에서 참는 것이 이 계획의 가장 어려운 부분이다.** 기준선 없이 고치면
좋아졌는지 나빠졌는지 말할 수 없고, 그러면 6개월 뒤 다시 같은 자리에 선다.

## 6. 하지 말아야 할 것

- **오디오 클립을 저장하는 것** — 전사문과 신호값이면 충분하다. 오디오는 위험만 늘린다
- **기록 없이 프롬프트부터 고치는 것** — 좋아졌다고 말할 근거가 안 생긴다
- **주기를 무작정 줄이는 것** — 25초를 10초로 하면 비용이 2.5배인데 정확도는 오히려 떨어진다.
  짧을수록 문맥이 없다
- **피드백 버튼을 세 개 이상 두는 것** — 회의 중이다. 안 누른다
- **경보를 늘리는 것** — 2026-08-24 에 "등록한 목소리가 붙지 않았습니다" 가 거짓 경보였던 것을
  이미 겪었다. **너무 자주 외치는 경보는 꺼지지 않는 경보와 같다**

## 7. 정해 주셔야 하는 것

1. **전사문을 저장해도 되는가.** 지금은 한 글자도 안 남긴다. 1겹의 전제이자
   이 계획 전체의 전제다. 남긴다면 **동의 문구를 먼저 고쳐야 한다** —
   현재 동의 창은 "25초마다 전사·판정됩니다" 라고만 말하고 **보관한다는 말은 없다**
2. **보관 기간.** 90일? 1년? 미팅이 지워지면 함께 지울 것인가
3. **피드백 버튼을 회의 중에 노출할 것인가**, 아니면 회의가 끝난 뒤 타임라인에서 한 번에 받을 것인가
   — 회의 중이 정확하지만 방해가 되고, 끝난 뒤는 편하지만 기억이 흐려진다
4. **비용 상한.** 기본이 켜짐이 된 지금, 1시간 회의당 288회다.
   상한을 둘 것인가(예: 회의당 200회 뒤 주기를 60초로 늘림)

1번이 "안 된다" 면 이 계획은 성립하지 않는다. 그때는 **개인정보를 남기지 않는 신호값만**
(전사문 없이 숫자만) 저장하는 축소판으로 다시 짜야 한다 — 가능하지만 훨씬 느리게 좋아진다.
