# R2 녹음 백업 계획 (2026-08-13)

## 왜 지금인가

녹음 파일 훈련을 붙이다가 확인했다. **R2 에 사본이 하나뿐이다.**
버전관리도 복제도 걸려 있지 않다. 지워지면 끝이고, 덮어써져도 끝이다.

DB 는 다르다. Neon 이 시점 백업을 갖고 있고, 2026-08-13 에 실제로 되돌려서
12개 테이블 2,461행이 해시까지 일치하는 것을 확인했다. 녹음은 그 대조군이 없다.

지금 규모: **녹음 44개 · 합계 172분 · 경로 없는 행 0개** (2026-08-13 실측).
바이트는 R2 자격증명이 없어 못 쟀다. 길이로 추정하면 40~80MB 정도다.

## 확인한 사실

Cloudflare 문서에서 확인한 것이고, 추정이 아니다.

| | |
|---|---|
| 버킷 간 복제 | **없다** — S3 CRR 같은 기능이 R2 에는 없다 |
| 객체 버전관리 | **없다** |
| 이벤트 알림 | `object-create`(Put·Copy·CompleteMultipart) / `object-delete`(Delete·LifecycleDeletion) → Queue → 소비 Worker |
| 수명주기 규칙 | 나이·날짜 기준 만료, 스토리지 클래스 전환. 버킷당 1000개 |
| 요금 | 저장 $0.015/GB·월 · Class A $4.50/100만 · Class B $0.36/100만 · **이그레스 무료** |
| 무료 한도 | 저장 10GB·월 · Class A 100만 · Class B 1000만 |

**복제 기능이 없다는 것이 이 계획의 출발점이다.** 만들어야 한다.

## 무엇을 막으려는가

이 코드베이스에서 **실제로 일어난 순서**대로 적는다. 가정이 아니다.

1. **우리 코드가 지운다.** v1 의 `purge_expired_meetings()` 는 이미 Storage 객체를
   하드 삭제한다. v2 에 같은 것이 생기면 같은 위험이 생긴다.
2. **고정 키 덮어쓰기.** v2 에서 실제로 났던 사고다. 고쳤지만, 같은 종류는 또 난다.
3. **사람이 콘솔에서 지운다.**
4. **계정·토큰 유출.** 앞의 셋과 성격이 다르다 — **같은 계정 안의 백업으로는 못 막는다.**

1~3 이 압도적으로 흔하고, 이 계획은 거기에 맞춘다. 4 는 4단계에서 따로 다룬다.

## 설계 결정 셋

### 1. 백업은 **절대 지우지 않는다**

`object-delete` 를 따라가면 그건 백업이 아니라 복제다. 사고를 그대로 전파한다.
프로덕션에서 지워진 것은 백업에 **남아 있어야** 쓸모가 있다.

CLAUDE.md 의 원칙과 같다 — 자동으로 지우는 청소기를 만들지 않는다.

### 2. 키에 시각을 붙인다

덮어쓰기를 살리려면 백업에서 같은 키를 덮으면 안 된다.
`<원래키>` 가 아니라 `<원래키>/<업로드시각>` 으로 넣는다.
같은 키가 두 번 오면 둘 다 남는다.

### 3. 보존 기한과 부딪힌다 — 미리 정면으로 본다

v1 은 `retention_days` 기본 **90일**이고 purge 가 하드 삭제한다. 고객에게 한 약속이다.
백업이 영원히 들고 있으면 **그 약속이 깨진다.**

v2 는 지금 **보존 기한 자체가 없다.** 그래서 당장은 충돌하지 않지만,
보존 정책을 넣는 순간 백업 창을 같이 정해야 한다. 미뤄 두면 나중에
"백업에 남아 있는 건 몰랐다" 가 된다.

→ **백업 창 30일**을 제안한다. 사고는 며칠 안에 발견된다. 30일이면 사고에는 충분하고,
   나중에 90일 보존을 넣어도 그 안에 들어간다.
→ 만료는 수명주기 규칙으로 자동화하되, **무엇이 지워질지 목록을 먼저 남긴다.**

## 두 가지 방식

| | A. 이벤트 → Queue → Worker | B. 정기 훑기 (Actions) |
|---|---|---|
| 지연 | 초 단위 | 최대 6시간 |
| 프로덕션에 새 표면 | Worker·Queue 추가 | **없음** |
| 덮어쓰기 **이전** 바이트 | 못 살림 (이벤트는 쓰기 뒤에 온다) | 못 살림 |
| 한 번 놓친 파일 | **영영 안 들어온다** (큐가 흘리면 끝) | **다음 회차가 메운다** |
| 복잡도 | 높음 | 낮음 |
| 이미 있는 것 재사용 | 없음 | 훈련 워크플로 그대로 |

### B 를 추천한다

셋 때문이다.

- **자가 복구.** B 는 매 회차가 두 버킷 전체를 대조한다. 한 번 놓쳐도 다음에 들어온다.
  A 는 큐가 한 번 흘린 파일이 영영 백업되지 않고, **그 사실을 알 방법도 없다.**
- **프로덕션에 아무것도 안 붙인다.** 외부에 드러나는 표면을 늘리지 않는다.
- **6시간 지연이 지금 실질 위험이 아니다.** 녹음 44개짜리 서비스이고,
  잃는 시나리오는 "방금 올린 것" 이 아니라 "몇 달 전 것을 뭔가가 지웠다" 쪽이다.

규모가 커져 6시간이 부담되면 그때 A 를 **B 위에 얹는다.** B 를 걷어내지 않는다 —
자가 복구는 계속 필요하다.

## 단계

### 1단계 — 버킷과 토큰 *(사람이 한다. 내가 하지 않는다)*

- R2 버킷 `sep-v2-uploads-backup` 생성
- API 토큰 발급 — 범위를 **이 두 버킷으로만** 제한
- GitHub 시크릿 셋: `CLOUDFLARE_API_TOKEN` · `CF_ACCOUNT_ID` · `R2_BACKUP_BUCKET`

> **솔직히 적어 둘 것:** R2 API 토큰에는 "쓰기는 되고 삭제는 안 됨" 등급이 없다.
> Object Read only / Object Read & Write 뿐이다. 그래서 **이 토큰이 새면 백업도 지워질 수 있다.**
> 같은 계정 안에서는 이 구멍을 못 막는다. 4단계가 그 답이다.

같은 시크릿으로 `db.yml` 의 R2 감사도 살아난다 — 지금 그 워크플로는 시크릿이 없어 못 돈다.

### 2단계 — 훑어 넣기 `worker/tools/r2-backup.js`

- 두 버킷 목록을 각각 끝까지 읽는다 (커서를 끝까지 — 잘라 읽으면 있는 파일을 없다고 판정한다)
- 백업에 없는 것만 복사한다. **지우는 코드는 넣지 않는다**
- 6시간마다 + 수동 실행
- 로그: `새로 넣음 N개 · 이미 있음 M개 · 합계 X MB`

### 3단계 — 백업이 **진짜인지** 검증 *(audio-drill 확장)*

여기가 핵심이다. 복사했다는 것과 되살아난다는 것은 다른 말이다.

- 프로덕션 객체마다 백업 대응물이 있고 **크기가 같은가**
- **백업 쪽에서** 표본을 내려받아 `ffprobe` 로 열고, DB 가 아는 길이와 맞는가

이걸 빼면 "복사는 됐다" 까지만 알고 정작 필요한 날에 처음 열어 보게 된다.
DB 훈련에서 이미 겪었다 — 세 번 실패한 것이 전부 그런 종류였다.

### 4단계 — 계정 밖으로 *(2026-08-15 진행)*

**두 번째 Cloudflare 계정**으로 정했다. 같은 R2 API 라 코드가 거의 같고,
다른 사업자를 하나 더 배우는 값보다 지금 붙는 값이 크다고 봤다.
같은 사업자라 Cloudflare 전체 장애는 못 막지만, **계정 정지·결제 실패·관리자 자격증명
유출**은 막힌다 — 그게 원래 4단계의 목적이었다.

`worker/tools/offsite-backup.js` · `R2 backup` 워크플로에 함께 돈다.

- **원본에서 읽는다.** 사본의 사본이면 백업 쪽 잘못을 그대로 물려받는다.
  따로 읽으면 두 사본이 서로를 검증한다. 이름 규칙은 백업과 같다
- **자격증명이 갈라져 있다.** 읽기는 1계정 토큰, 쓰기는 2계정 토큰.
  한쪽이 새도 다른 쪽 사본은 남는다 — 이 단계의 존재 이유다
- 두 계정 ID 가 같으면 **실패**로 끝난다. 아무것도 못 막으면서 도는 것이 제일 나쁘다

### 3.5단계 — 버킷 잠금 *(2026-08-15 걺)*

계획을 세울 때는 몰랐던 것이다. R2 에 **버킷 잠금**이 있고, 지정 기간 동안
**삭제와 덮어쓰기를 막는다.** 백업 버킷에 30일로 걸었다 — 합의한 백업 창과 같다.

바꾸려면 '버킷 설정 편집' 권한이 필요하다. 백업 토큰이 `Object Read & Write` 면
잠금을 못 건드리므로, **토큰이 새도 백업이 남는다.**

**다만 2026-08-15 현재 백업 토큰은 잠금을 걸 수 있었다** — 권한이 그보다 넓다는 뜻이고,
지금 잠금은 실수는 막지만 그 토큰의 유출은 못 막는다. 토큰을 `Object Read & Write` 로
낮춰야 한다.

> ~~백업 작업은 객체 읽기·쓰기만 하므로 낮춰도 그대로 돈다.~~
>
> **이 문장이 틀렸다 (2026-08-24 정정).** 그날 토큰을 낮췄고 **백업이 그 자리에서
> 멈췄다** — 마지막 성공 `2026-08-15 08:28Z`, 이후 28회 연속 실패.
>
> 백업 도구가 쓰던 `client/v4/.../r2/buckets/{b}/objects` 는 **계정 단위 권한**을
> 요구한다. `Object Read & Write` 토큰은 **S3 호환 API 용**이라 거기서는 403 이다.
> "객체 읽기·쓰기만 한다" 는 맞았지만 **어느 API 로 하느냐**를 안 봤다.
>
> 고친 방향은 토큰을 도로 넓히는 것이 **아니다.** 그러면 이 절이 없애려던 구멍이
> 그대로 돌아온다. **도구를 S3 API 로 옮겼다** (`worker/tools/r2-s3.js`).
> 이제 권한이 두 갈래다:
>
> | | API | 토큰 | 언제 |
> |---|---|---|---|
> | 객체 (목록·읽기·쓰기) | S3 | `Object Read & Write` | **6시간마다** |
> | 버킷 (목록·생성·잠금) | client/v4 | 넓은 토큰 | 사람이 손으로 켤 때만 |
>
> 예약 실행은 넓은 토큰이 **아예 필요 없다.** 잠금을 못 읽으면 "못 봄" 이라고 적고
> 넘어간다 — 그것이 바라는 상태다. 못 읽는다는 것은 못 푼다는 뜻이다.

## 백업 키가 처음부터 `/undefined` 였다 (2026-08-25 발견)

백업 키를 `<원래키>/<업로드시각>` 으로 지은 이유는 이것이었다.

> 덮어쓰기 사고를 살리려면 백업에서 같은 키를 덮으면 안 된다.

**그런데 그 시각이 계속 `undefined` 였다.** client/v4 의 객체 목록 응답에 우리가
읽던 `uploaded` 필드가 없었고, 52개 사본이 전부 `<원래키>/undefined` 한 칸을
쓰고 있었다. 넣는 쪽과 대조하는 쪽이 같은 필드를 봐서 **자기들끼리는 앞뒤가 맞았고,
여태 `OK` 로 보고돼 왔다.**

그래서 **원본을 덮어쓰면 사본도 같이 덮였다.** 지키려던 성질이 처음부터 안 지켜졌다.

S3 로 옮기면서 `LastModified` 가 진짜 값으로 들어오자 키가 전부 어긋났고,
**버킷을 통째로 다시 올리는 것을 막으려고 넣어 둔 가드가 그 자리에서 걸렸다.**
가드가 없었으면 조용히 한 벌 더 쌓고 `OK` 를 냈을 것이고, 이 결함은 계속 안 보였다.

바로잡는 길은 한 번 다시 올리는 것뿐이다 (`allow_rekey`). 옛 `/undefined` 사본은
미아로 남는다 — 30일 잠금이 걸려 있어 지울 수도 없고, 이 도구에는 지우는 코드가 없다.

### 30일을 어떻게 구현했나 — 세지만 지우지 않는다

수명주기 규칙으로 자동 만료를 걸지 **않았다.** 백업 작업은 30일 지난 객체를
**세어서 보여주고 그대로 둔다.**

CLAUDE.md 의 원칙이다 — 자동으로 지우는 청소기를 만들지 않는다. 그리고 지금은
지워야 할 이유도 없다: 추정 40~80MB 로 무료 한도(10GB) 한참 아래이고,
v2 에는 아직 보존 기한 자체가 없어서 30일을 넘겨 갖고 있는 것이 어떤 약속도 깨지 않는다.

**보존 정책을 넣는 날** 이 창이 실제 의미를 갖는다. 그때 아래 한 줄로 켠다:

```bash
npx wrangler r2 bucket lifecycle add sep-v2-uploads-backup \
  --name expire-30d --expire-days 30
```

지금 켜 두면 "왜 백업이 사라졌지" 를 나중에 아무도 설명 못 한다.
