# LEP 설계 — SEP 와 무엇이 다른가

- 작성일: 2026-08-25 · 기준 `2.1.0` (SEP v2.18.0 포크)
- 무엇인가: **자원을 세우기 전에** 무엇을 바꿀지 정하는 문서
- 상태: **기획. 착수 전.** §8 「정해 주셔야 하는 것」이 먼저다

---

## 0. 한 줄

**SEP 의 기능은 전부 그대로 두고, 그 위에 두 겹을 얹는다** —
사무장 업무(사건·기한·이해충돌)와 법률 상담 분석(사실/주장/요건·누락·타임라인·비닉권).

엔진(녹음 → 전사 → 화자 → 분석 → 노트, 실시간 자막·코칭)은 **건드리지 않는다.**
거기서 나오는 산출물의 **모양만** 바꾼다. 그래야 SEP 에서 검증된 것을 잃지 않는다.

**그리고 모든 미팅이 사건 상담인 것은 아니다** (§1.5). 변호사도 일반 미팅을 한다 —
그런 자리에 법률 분석을 걸면 요건사실이 전부 `MISSING` 으로 나온다.
**아무 문제 없는 대화에 대고 빠진 것 투성이라고 외치는 것**이고, 그건 SEP 에서 두 번 밟은
거짓 경보와 같은 모양이다. 그래서 **미팅 종류가 분석 방식을 정한다.**

## 1. 무엇이 같고 무엇이 다른가

| | SEP (영업) | LEP (법률) |
|---|---|---|
| 만나는 상대 | 고객사 담당자 | **의뢰인** |
| 중심 단위 | 고객사 → 미팅 | **의뢰인 → 사건(Matter) → 상담** |
| 분석의 목적 | 딜을 이기는 것 | **사실관계를 정확히 세우는 것** |
| 요약이 답하는 질문 | 무엇을 말했나 | **무엇이 빠졌나 · 어긋나나** |
| 점수 | 영업 역량 6종 | **요건사실 충족도 · 입증 가능성** |
| 시간 | 다음 미팅 일정 | **시효 · 기일 · 통지 기한** — 놓치면 사건이 진다 |
| 실시간 코칭 | 지금 이렇게 말하세요 | **지금 이걸 물어보세요** |
| 유출의 대가 | 영업 정보 노출 | **회복 불가능한 법적 손실** |
| 삭제 | 사용자 편의 | **보관·파기가 의무이자 위험** |

**그대로 쓰는 것** — 구간 녹음(10분), 실시간 자막, 전사·화자 분리, 녹취 편집·재생,
등록 목소리 실명 귀속, 코칭 판정 기록(`coaching_events`), 조용한 등급 강등 방지,
경보의 비대칭(위험은 두 번 확인), 미첨부 녹음 노출.

## 1.5 미팅 종류 — **모든 미팅이 사건 상담은 아니다**

이 문서의 첫 판은 `의뢰인 → 사건 → 상담` 을 **필수 삼층**으로 잡았다. 틀렸다.
변호사의 하루에는 사건과 무관한 자리가 섞여 있다 — 수임 전 상담, 자문 문의,
소개·네트워킹, 사무소 내부 회의, 거래처 미팅.

**종류를 먼저 정하고, 그것이 분석·코칭·보호 수준을 전부 정한다.**

| 종류 | 사건 | 분석 | 실시간 코칭 | 비닉권 |
|---|---|---|---|---|
| **상담 (법률)** | 필수 | `legalAnalysis` — 사실/주장/요건·누락·타임라인·증거 | 이걸 물어보세요 | **적용** |
| **수임 상담 (BD)** | 선택 | **SEP 영업 분석 그대로** — 수임을 따내는 것은 영업이다 | 이렇게 말해보세요 | 적용 |
| **일반** | 없음 | 요약·핵심·후속 조치만. **점수도 요건도 없다** | 끔이 기본 | 미적용 |

**SEP 의 영업 분석이 버려지는 기능이 아니라 하나의 모드가 된다.**
수임 상담은 실제로 영업이다 — "기능을 모두 전수한다" 는 요구가 여기서 가장 잘 맞는다.

### 어떻게 정해지나

- **사건이 붙어 있으면 상담(법률)이다.** 자동으로 그렇게 둔다
- 사건이 없으면 **기본은 일반**이다. 법률 분석을 잘못 거는 쪽이 그 반대보다 나쁘다 —
  일반으로 돌린 상담은 나중에 다시 돌리면 되지만, 일반 대화에 대고 요건 누락을 외치면
  **다음부터 아무도 그 화면을 안 본다**
- **화면이 종류를 항상 보여 준다.** 조용히 정해지지 않는다
- 다시 돌릴 수 있다 — 분석만 지우는 경로가 이미 있다(SEP `2.11.0` 전수)

### 언제 정해야 하나 — **녹음 시작 전이다**

실시간 코칭이 종류에 따라 다른 것을 말하므로 **녹음을 누르기 전에** 정해져야 한다.
SEP 는 미팅을 녹음이 끝난 뒤에 만든다(구간이 `meeting_id` 없이 먼저 올라간다).
그래서 종류는 **녹음 화면에서 고르고**, `/risk` 호출과 미팅 생성 양쪽에 실린다.

기본값은 **일반**이다. 고르지 않고 녹음을 시작해도 안전한 쪽으로 떨어진다.

## 2. 도메인 — 사무장 업무를 담는 자리

### 2.1 사건(Matter)이 중심이 된다

SEP 는 `customers → meetings` 두 층이다. 법률사무소는 **사건이 있을 때만** 세 층이다.

```
의뢰인(client)  ──▶  사건(matter)  ──▶  상담(meeting)      ← 사건이 있는 자리
                        │
                        ├─▶ 기한(deadline)      시효·기일·제출·통지
                        ├─▶ 증거(evidence)
                        ├─▶ 타임라인(timeline_event)
                        └─▶ 상대방(adverse_party)

의뢰인(client)  ─────────────────────▶  미팅(meeting)      ← 수임 전·자문 문의
                                          (matter_id 없음)

                                       미팅(meeting)      ← 내부 회의·거래처
                                          (customer_id·matter_id 둘 다 없음)
```

**`meetings.matter_id` 도 `customer_id` 도 필수가 아니다.** 사건이 없는 미팅이 정상이고,
의뢰인조차 없는 미팅도 정상이다. 사건·기한·이해충돌은 **사건이 있을 때만** 걸린다.

**`customers` 를 `clients` 로 이름을 바꾸지 않는다.** 서비스·라우트·화면이 전부 그 이름을 쓰고,
바꾸면 검증된 코드를 통째로 흔든다. **`customers` 를 의뢰인 표로 그대로 쓰고**
`matters` 를 새로 얹는다. 화면 문구만 "고객사" → "의뢰인" 으로 바꾼다.
(이름과 뜻이 어긋나는 것은 알고 있다 — 그 값보다 안정성이 크다고 봤다. 나중에 옮길 수 있다.)

### 2.2 이해충돌 검사 — 사무장 업무의 첫 관문

신규 의뢰를 받기 전에 **상대방이 기존 의뢰인인지** 확인해야 한다. 이걸 놓치면 수임 자체가 문제가 된다.

`adverse_parties` 에 사건별 상대방을 쌓고, 새 의뢰인·상대방 이름이 들어올 때 대조한다.
**자동으로 막지 않는다. 목록을 보여 주고 사람이 정한다** — `CLAUDE.md` 의 원칙 그대로다.
이름은 표기가 흔들리므로(주식회사/㈜/영문) 정규화해 비교하고, **의심되면 보여 준다.**

### 2.3 기한 — 놓치면 사건이 진다

SEP 의 `action_items` 는 "다음에 할 일" 이다. 법률에서는 **날짜가 법적 효력**을 가진다.

`deadlines`: 기한 종류(소멸시효·제척기간·항소기한·서면제출·기일·통지), 기준일, 계산 근거,
D-day, 확정/추정 구분. **추정한 기한은 반드시 그렇다고 표시한다** —
AI 가 계산한 시효를 확정으로 보여 주면 그게 사고다.

## 3. 분석 — 네 원칙을 코드로

### 3.1 사실 / 주장 / 요건 분리

지금 `analysis_results` 는 영업용이다(`customer_needs`·`deal_signals`·`scores`).
LEP 는 **새 표에 따로 담는다** — 기존 표를 비틀지 않는다.

```
statements          진술 하나하나
  kind              fact | claim | opinion | hearsay | unknown
  speaker           누가 (전사 화자 라벨)
  segment_id        어느 발화에서 왔나  ← 근거로 되짚을 수 있어야 한다
  certainty         모델의 확신도
  adverse           의뢰인에게 불리한가

legal_elements      이 사건에 필요한 요건사실 (청구원인별 체크리스트)
  cause             채무불이행 · 불법행위 · 부당이득 …
  element           채무의 존재 · 이행기 도래 · 귀책사유 · 손해 · 인과관계 …
  status            satisfied | partial | missing | contested

element_statements  요건 ↔ 진술 연결 (다대다)
```

> **"A사가 납기를 늦춰 프로젝트에 차질이 생겼다"** 를
> 사실(계약서상 납기일·실제 납품일) / 주장(상대방 과실) / 요건(채무불이행 성립·인과관계)
> 으로 갈라 담는 것이 이 표들의 전부다.

**`segment_id` 를 반드시 붙인다.** 근거 없는 분류는 법률 문서에서 쓸모가 없다 —
"모델이 그렇게 말했다" 는 답이 되지 않는다. 원 발화로 한 번에 돌아갈 수 있어야 한다.

### 3.1.1 판정 계약 — 페르소나는 코드에 있다

분석의 지시문은 **사용자(법률 실무자)가 직접 정한 것**이고,
`worker/src/services/legalAnalysis.ts` 에 **문구 그대로** 들어 있다.
문서와 코드에 프롬프트가 흩어지면 어느 쪽이 실제인지 알 수 없게 되므로 **코드가 원본**이다.

> 당신은 대한민국 법률 실무에 정통한 **시니어 수석 소송 전문 변호사 보조 AI**입니다.
> … 사실과 주장의 엄격한 분리 · 불리한 사실 및 진술 모순 식별 · 증거 매핑 · Strict JSON Output

**출력은 JSON Schema 로 강제한다**(`response_format: json_schema`, `strict: true`).
`temperature: 0` 이다 — 사실관계 분해에서 창의성은 해롭고, 같은 녹취에서 같은 답이 나와야 한다.

| 갈래 | 무엇 |
|---|---|
| `chronological_facts` | **객관적 행위만.** 각 사실에 증거(`kind`·`status`·`holder`·`difficulty`)가 1:1로 붙는다 |
| `claims` | 의뢰인의 주관적 주장. 사실과 **섞지 않는다**. 근거가 된 사실 id 를 가리킨다 |
| `legal_elements` | 청구원인별 요건. `SATISFIED / PARTIAL / MISSING / CONTESTED` |
| `risk_and_gaps` | 누락·모순·불리한 사실·가정. **모순은 반드시 둘 이상을 가리킨다** |
| `next_questions` | 다음 상담에서 확인할 것 |

증거 상태는 사용자가 정한 넷이다 — `SECURED` · `PROMISED` · `UNCONFIRMED` · `NON_EXISTENT`.
**"있다" 와 "가져올 수 있다" 를 가르는 것**이 이 enum 의 값이다.

페르소나 옆에 **가드레일**을 따로 두었다. 페르소나가 *무엇을 하는가*를 정하고,
가드레일은 *하지 말아야 할 것*을 정한다 — 없는 날짜·금액을 추론해 채우지 말 것,
`risk_and_gaps` 가 없으면 빈 배열로 둘 것(억지로 채우면 거짓 경보다),
법적 결론을 단정하지 말 것(최종 판단은 변호사가 한다).
페르소나는 사용자의 것이고 가드레일은 우리가 사고를 밟으며 더할 자리라 나눠 두었다.

**아직 워크플로에 연결하지 않았다.** 담을 표(`018~020`)와 §8① 의 판단이 먼저다.

### 3.2 누락과 모순 — 이쪽이 더 어렵고 더 값어치 있다

일반 요약은 **말한 것**을 줄인다. 여기서는 **말하지 않은 것**을 찾는다.

```
findings
  kind        gap | inconsistency | adverse_fact | assumption
  severity    낮음 | 보통 | 높음
  detail      무엇이 어긋나는가
  refs        관련 진술 id 들   ← 모순은 최소 둘을 가리켜야 한다
  question    이걸 풀려면 무엇을 물어야 하나
```

- **gap(누락)** — `legal_elements` 에서 `missing` 인 것이 곧 누락이다. **계산으로 나온다.**
  모델에게 "빠진 게 뭐냐" 고 묻는 것보다 확실하다.
- **inconsistency(모순)** — 같은 사실에 대한 두 진술이 어긋나는 경우. 반드시 **양쪽을 가리킨다.**
- **adverse_fact(불리한 정황)** — 의뢰인이 축소하거나 흘리듯 말한 것.
  **찾아서 크게 보여 준다.** 변호사가 법정에서 처음 알면 그때는 늦다.

**이 셋은 "정상" 을 만들지 않는다.** 없으면 없다고만 적는다 — SEP 에서 배운 것이다.
거짓 경보가 잦으면 아무도 안 본다.

### 3.3 타임라인 + 증거

```
timeline_events
  occurred_on      일자 (불명이면 범위와 근거)
  precision        exact | month | year | unknown
  what             무슨 일이
  legal_meaning    법적 의미 (계약 체결 · 통지 도달 · 시효 기산 …)
  segment_id       어느 발화에서

evidence
  kind             계약서 · 문자 · 이메일 · 녹취 · 이체내역 · 증인 …
  holder           의뢰인 보유 | 상대방 보유 | 제3자 | 없음
  difficulty       1~5 (확보 난이도)
  proves           어느 진술/이벤트를 입증하나
```

**입증 난이도를 1:1로 매긴다.** "증거가 있다" 와 "증거를 가져올 수 있다" 는 다르다.
상대방이 가진 문서는 있어도 못 쓸 수 있고, 그 사실이 전략을 바꾼다.

### 3.4 비닉권과 PII — **이것이 나머지 셋의 전제다**

사용자 말 그대로다: *유출 시 회복 불가능한 법적 손실.*
그래서 SEP 에서 "기록이 먼저" 였던 자리에, 여기서는 **보호가 먼저**다.

| 무엇 | 어떻게 |
|---|---|
| **비식별화** | 전사문에서 주민번호·계좌·전화·주소를 찾아 치환하고, 원문↔치환의 대응은 **분리 보관**. 모델에 나가는 것은 치환본 |
| **비닉권 표시** | 상담 기록은 기본이 `privileged`. 내보내기·인쇄에 그 표시가 자동으로 박힌다 |
| **접근 감사** | **누가 언제 무엇을 열었는지 전부 남긴다.** 증거개시 다툼에서 이 기록이 방패다 |
| **최소 노출** | 사건 담당자만 본다. 관리자라고 전부 보이지 않는다 — SEP 는 관리자가 전체를 본다. **여기서는 그게 위험이다** |
| **파기** | 사건 종결 + 보관기간 뒤 파기. **자동으로 지우지 않고 목록을 보여 준다** |

**그런데 지금 구조는 상담 내용이 밖으로 나간다** — OpenAI(전사·분석), Deepgram·Google(실시간 자막).
비식별화를 해도 **대화 맥락 자체가 나간다.** 이건 기술 결정이 아니라 **법률·정책 결정**이라
§8 로 올린다. 내가 정할 수 있는 것이 아니다.

## 4. 실시간 — "이렇게 말하세요" 에서 "이걸 물어보세요" 로

SEP 코칭의 **구조는 그대로 값어치가 있다.** 경보 비용의 비대칭, 3초 안에 읽을 수 있는 문장,
회의 중 두 글자 피드백, 판정 기록 — 전부 유지한다. **내용만 법률로 바꾼다.**

| SEP 등급 | LEP 등급 | 언제 |
|---|---|---|
| 정상 | 정상 | 특이 신호 없음 |
| 주의 | **확인 필요** | 요건사실이 아직 안 나왔다 · 날짜가 모호하다 |
| 위험 | **위험** | 시효 임박 · 이해충돌 신호 · 불리한 사실이 흘러나옴 |
| 기회 | **단서** | 입증 가능한 증거가 언급됨 — 지금 확보를 요청해야 한다 |

`script` 가 **질문**이 된다.
- SEP: *"구독 방식에 대해 우려하시는 것 같네요. 어떤 점이 걱정되시는지…"*
- LEP: *"그 문자 받으신 게 몇 월이었는지 기억나시나요? 문자는 지금도 갖고 계신가요?"*

**위험만 두 번 확인하는 비대칭은 유지한다.** 의뢰인 앞에서 화면이 빨개지면
변호사의 말이 흔들리는 것은 영업과 똑같다.

## 5. 마이그레이션 계획

`001~015` 는 SEP 스키마 그대로 적용한다(기능 전수). **LEP 것은 `016` 부터.**

| | 무엇 | 왜 이 순서 |
|---|---|---|
| `016` | `meetings.kind` (`legal`/`business`/`general`, 기본 `general`) | **가장 먼저다.** 이게 없으면 분석이 무엇을 할지 모른다 |
| `016` | `matters` · `adverse_parties` · `meetings.matter_id` (**nullable**) | 나머지 전부가 사건에 붙는다 |
| `017` | `deadlines` | 사무장 업무의 핵심. 분석 없이도 값어치가 있다 |
| `018` | `statements` · `legal_elements` · `element_statements` | 3.1 |
| `019` | `findings` | 3.2 — `legal_elements` 가 있어야 gap 이 계산된다 |
| `020` | `timeline_events` · `evidence` | 3.3 |
| `021` | `access_log` · `pii_map` · `privileged` 플래그 | 3.4 |

**`021` 을 마지막에 두었지만 실제로는 가장 먼저 정해야 한다** — §8 의 답에 따라
`018~020` 이 무엇을 저장할 수 있는지가 달라지기 때문이다.

## 6. 화면

- **사건 화면** 신설 — 사건 하나에 상담·기한·타임라인·증거·요건 체크리스트가 모인다
- **녹음 화면 맨 위에 미팅 종류 선택** — 녹음을 누르기 전에 정해져야 한다(§1.5). 기본 `일반`
- **미팅 상세**에 탭 추가: `사실관계` · `타임라인` · `증거` · `확인할 것`
  — **상담(법률)일 때만 보인다.** 일반 미팅에 빈 탭 넷을 띄우지 않는다
- **대시보드**를 기한 중심으로 — "이번 주 기일 3건, D-7 이내 시효 1건"
- 문구: 고객사 → 의뢰인, 미팅 → 상담, 액션 아이템 → 후속 조치
- 내보내기에 **비닉권 표시** 자동 삽입

## 8. 정해 주셔야 하는 것

**① 상담 내용을 외부 AI 에 보내도 되는가** — **정해졌다 (2026-08-25).**

> **외부 AI 파이프라인을 그대로 쓰고, 그 위에 보호 장치를 얹는다.**
> SEP v2 코드를 가장 많이 재사용하는 길이고, "그대로" 와 "전부 자체" 사이의 절충이다.

즉 전사·분석·자막은 지금 경로(OpenAI · Deepgram · Google) 그대로 두고,
**보내기 전에 가리고, 누가 봤는지 남기고, 보이는 범위를 좁힌다.**

| 그대로 두는 것 | 새로 얹는 것 |
|---|---|
| OpenAI 전사·분석 | 보내기 전 **PII 비식별화** (주민번호·계좌·전화·주소) |
| Deepgram·Google 자막 | **접근 감사** — 누가 언제 무엇을 열었나 |
| 구간 녹음·화자 분리·노트 | **최소 노출** — 담당자만. 관리자 전체 열람 금지 |
| 실시간 코칭 구조 | **비닉권 표시** — 내보내기·인쇄에 자동 삽입 |

**대가를 적어 둔다** — 비식별화를 해도 **대화 맥락은 밖으로 나간다.**
이 선택은 그것을 감수하고 위탁계약·감사·최소노출로 관리하겠다는 뜻이다.
법률 검토에서 결론이 달라지면 `021` 을 먼저 고치고 파이프라인을 바꾼다.

**~~① (원문)~~** 이 문서 전체의 전제였다.
지금 구조는 OpenAI(전사·분석)와 Deepgram·Google(실시간 자막)로 대화가 나간다.
비식별화를 해도 맥락은 나간다. 세 갈래다.

- ~~그대로 간다~~ ← **선택됨**
- ~~전사만 외부, 분석은 자체 모델~~
- ~~전부 자체~~

**② 실시간 자막을 켤 것인가.** 자막은 음성이 **계속** 밖으로 흐른다. 상담에서는
①보다 노출이 크다. LEP 에서는 기본을 끄는 것도 방법이다(SEP 는 8/24 에 켬으로 바꿨다).

**③ 관리자가 모든 사건을 볼 수 있어야 하는가.** SEP 는 그렇다. 법률사무소에서는
**담당자만** 보는 것이 맞을 수 있다. 이건 코드 여러 곳에 걸리므로 일찍 정해야 한다.

**④ 요건사실 체크리스트를 어디까지 내장할 것인가.** 사건 유형마다 다르다.
처음부터 넣을 청구원인을 몇 개로 시작할지 — 예: 채무불이행 · 불법행위 · 부당이득 ·
임대차 · 이혼/재산분할. **변호사가 직접 정해 주셔야 한다.** 제가 만들면 틀린다.

**⑤ 미팅 종류를 셋으로 둘 것인가.** `상담(법률)` · `수임 상담(BD)` · `일반` 로 잡았다.
BD 를 따로 두는 것은 SEP 의 영업 분석을 그대로 살리기 위해서인데, 실제 업무에서
수임 상담과 일반 상담이 잘 갈리지 않으면 **둘로 줄이는 편이 낫다** — 고르는 칸이 늘수록
아무도 안 고른다.

**⑥ 보관 기간과 파기 규칙.** 사건 종결 후 몇 년인가. 법정 보존 의무가 있는가.
