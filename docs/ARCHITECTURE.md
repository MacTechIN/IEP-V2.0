> **[LEP 포크 안내 — 2026-08-25]** 이 문서는 포크 시점의 SEP v2 구조 그대로다.
> 구조는 이어받았지만 **자원 이름은 다르다**: Worker `lep-api` · Pages `lep-web` ·
> R2 `lep-uploads` · DB 는 LEP 전용 Neon(아직 없음). 본문의 sep-v2-* 주소·이름은
> SEP 시절의 값이니 그대로 믿지 말 것. LEP 구조가 갈라지기 시작하면 본문을 고친다.

# SEP v2 — 지금 어떻게 짜여 있나

> **이 문서는 계획이 아니라 지금 돌고 있는 것을 적는다.**
> 8월 초의 구상은 `docs/MVP_V2.0_PLAN.md` 등에 있다 — 그것과 이 문서가 다르면 **이 문서가 맞다.**
>
> 마지막 확인: 2026-08-26 · 마이그레이션 `030` · 버전 `2.27.0` · 마이그레이션 `030` (LEP)

v1(`~/workspace/SEP`)은 **완전히 별개 제품**이다. 번호도 배포도 섞지 않는다.

  │    │

  │    ├─→ R2                               sep-v2-uploads
  │    ├─→ OpenAI                           전사 · 분석 · 코칭
  │    │
  │    └─→ Workflows
  │          ├─ sep-v2-transcribe           녹음 하나를 전사

권한 검사가 코드에 있다(v1 은 RLS 가 DB 에서 판정).

## 계층

| 계층 | 무엇 | 어디 |
|---|---|---|
| 화면 | React 19 + Vite + MUI | Pages 프로젝트 **`sep-v2-web`** |
| API | Hono on Cloudflare Workers | `sep-v2-api` · 엔드포인트 46개 |
| DB | Neon Postgres (스키마 `v2`) | Hyperdrive 경유 |
| 파일 | R2 | 버킷 `sep-v2-uploads` |
| 비동기 | Cloudflare Workflows × 2 | `sep-v2-transcribe` · `sep-v2-analysis` |
| 실시간 | Node + `ws` on Cloud Run | `sep-v2-stream` |
| AI | OpenAI · Deepgram · Google STT | 아래 표 |

**Hyperdrive 를 쓰는 이유**: 직접 연결은 요청마다 TLS 핸드셰이크와 Postgres 인증을 다시 해
**365ms** 가 들었다. Hyperdrive 가 연결을 재사용해 **72ms** 가 됐다.

## LEP 이 갈라진 곳 (마이그레이션 `016`–`022` · 2026-08-26)

포크 시점에는 SEP 그대로였다. **지금은 다음 넷이 다르다.**

### 1) 미팅 위에 **사건**이 있다

SEP 는 미팅이 최상위였다. LEP 는 **사건 하나에 상담·기한·요건·시계열·증거가 모인다** —
흩어져 있으면 사건을 파악할 수 없고, 그 한 화면이 이 제품의 값이다.

| 표 | 무엇 |
|---|---|
| `matters` | 사건. `privileged` 기본 참 · `retention_years` 는 **null 이면 파기 대상에 오르지 않는다** (`022`) |
| `adverse_parties` | 상대방. `name_norm` 이 이해충돌 검사의 열쇠다 |
| `deadlines` | 기한. `is_estimated` 가 **AI 가 뽑은 것과 사람이 넣은 것을 가른다** (`017`) |
| `legal_elements` | 청구원인별 요건 체크리스트. `v2.seed_legal_elements()` 가 깐다 (`018`) |
| `legal_elements` | 요건 체크리스트. **`set_by='human'` 이면 AI 분석이 덮지 않는다** (`025`) — v1 이 `action_items_done` 에서 낸 사고를 반복하지 않는다 |
| `timeline_events` · `evidence` | 증거 연계형 시계열. `precision` 으로 **날짜를 모르는 것을 아는 척하지 않는다** |
| `pii_masks` · `access_log` | 비식별화 되돌리기표 · 열람 감사 (`021`) |

**실시간 전사** (2026-08-26) — Cloud Run **`lep-stream`** (`asia-northeast3`).
Worker 에는 연결을 듣는 소켓이 없어 `ws` 가 돌지 않는다. **SEP 의 `sep-v2-stream` 을 같이 쓰지 않는다** —
비닉권 대상 음성이 SEP 서버를 지나가면 안 된다. GCP 프로젝트는 `sep2-505108` 을 함께 쓰지만
**서비스·시크릿(`lep-jwt`·`lep-deepgram`)은 별개다.**
`JWT_SECRET` 은 Worker 와 **같은 값**이어야 한다 — 다르면 자막이 401 로 조용히 안 뜬다.

**마이그레이션 기록** (`027`) — `v2.schema_migrations` 에 **적용과 같은 트랜잭션으로** 남는다.
같은 파일을 다시 돌리면 건너뛰고, **적용한 뒤에 바뀐 파일은 거부한다** —
`if not exists` 때문에 조용히 성공해서 DB 만 옛 모양으로 남는 것을 막는다.
`001`–`026` 은 소급 등록이라 체크섬이 `null` 이다(「모른다」는 뜻).

**분석이 덜 끝난 것** (`028`) — `meetings.analysis_note`. 실패는 아니지만 덜 된 것을 담는다.
**비어 있으면 온전히 끝난 것이다.** 전사 쪽 `transcribe_notes`(`014`)와 같은 자리.

**서면 생성** (`029`) — 상담 분석으로 소장 등 초안을 만든다.
**서식별 표를 만들지 않는다** — 다른 것은 내용이지 저장 구조가 아니다.
새 서식 = `services/documents/<서식>.ts` 하나 + 등록부 한 줄. 표·라우트·화면은 안 바뀐다.

무엇을 모델에게 **안** 맡기나 — 금액(`costs.ts` 가 계산), 당사자·법원·날짜(`render()` 가 박아 넣음).
**재료가 없으면 만들지 않는다** (`form.missing()` → 422). 빈자리를 모델이 채우면 그것이 사고다.
불리한 사실은 **감추지 않고 우리 언어로 먼저 규정한다** — 감추면 프레임을 상대가 잡는다.
전략 갈림길은 **변호사에게 꺼내 놓기만** 하고, 「변호사가 보태는 것」 이 자료를 이긴다.

**서면은 사건의 것이다.** 상담이 아니라 사건의 요건사실·시계열·증거로 만든다.
그래서 사건에 붙지 않은 상담에서는 만들 수 없다.

**사건을 지우는 것** (`2.22.0`, `services/matterExport.ts`) —
외래키가 무엇이 사라지고 무엇이 남는지 정한다. 서면·기한·요건·시계열·증거·상대방은
함께 사라지고(CASCADE), **상담·녹음·전사·분석은 남는다**(`matter_id` 만 비워진다).
지우기 전에 **개수까지 보여 주고**, 사건명을 손으로 적게 한다.
**사본은 안내가 아니라 구조로 남긴다** — 지우는 응답에 사본을 통째로 담아 돌려주고
화면이 그것을 들고 있는다. 「내려받으세요」 라고만 하면 지우려는 사람은 안 받는다.
자동으로 지우는 청소기는 만들지 않는다 — `purge_candidates` 는 목록일 뿐이다.

**끝난 상담을 사건에 붙이는 것** (`2.18.0`, `services/attach.ts`) —
`meetings.matter_id` 를 채우는 것으로 끝나지 않는다. 분석이 사건 없이 돌면
`legalPersist.ts` 는 원문과 findings 까지만 담고 멈추고(`if (!matterId) return`)
**시계열·증거·요건사실은 만들어지지 않는다.** 칸만 채우면 화면은 「붙었다」,
서면은 「자료가 없다」 가 된다. 그래서 붙일 때 **저장된 `legal_analyses.result` 로
파생 자료를 다시 만든다** — 모델을 다시 부르지 않으므로 돈이 들지 않고 몇 번을 해도 같다.
뗄 때는 `meeting_id` 로 이 상담이 만든 것만 지운다. **요건사실은 되돌리지 않는다** —
여러 상담이 덮어쓰는 표라 이 상담을 뺀 상태가 무엇인지 알 수 없다. 지어내느니 알려 준다.

**사용자를 지우는 것** (`023`·`024`) — `v2.users` 를 가리키는 외래키가 열여섯 개고
규칙이 셋으로 갈린다. 그냥 지우면 `matters` 가 `CASCADE` 라 **사건이 조용히 사라지고**
`meetings` 는 `NO ACTION` 이라 삭제를 막는다 — 가장 값진 것이 지워지고 덜 값진 것이 막는 꼴이다.
그래서 `v2.delete_user()` 가 **사건·상담·의뢰인·녹음·메일을 가진 사람을 거부한다.**
지우기 전에 `POST /admin/users/:id/transfer-matters` 로 넘긴다.
`access_log` 와 `deadlines.confirmed_by_email` 은 **계정이 사라져도 남는다.**

**미팅은 사건에 붙을 수도, 안 붙을 수도 있다.** `matter_id` 가 nullable 인 것이 설계다 —
첫 상담은 아직 사건이 아니고, 모든 미팅이 사건 상담도 아니다.
붙으면 요건·시계열·증거가 **사건 단위로 쌓이고**, 안 붙으면 상담 안에만 남는다.

### 2) 미팅 종류가 분석을 정한다 (`016`·`2.16.0`)

**법률 상담은 영업 분석기를 아예 부르지 않는다.** `analyzeMeeting`·`generateReport`·
`generatePsychCoaching`·`generateScorecard` 는 전부 영업 페르소나다 —
화면에서 감추는 것으로는 부족했다(감춰도 호출은 나가고 그 결과가 요약에 섞였다).
요약·할 일·확인 메일은 **법률 분해 한 호출**에서 나온다. 호출이 8 → 4 로 준다.
성과 화면·순위·스코어카드는 `kind <> 'legal'` 로 법률 상담을 뺀다.



`legal`(상담) · `business`(수임 상담) · `general`(일반). **기본은 `general`.**
일반 대화에 법률 분석을 걸면 요건이 전부 `MISSING` 으로 나와 거짓 경보가 된다.
실시간 코칭도 종류에 따라 다른 것을 묻는다.

### 3) 사건은 **담당자만** 본다

`getMatter()` 에 **관리자 우회가 없다.** SEP 의 관리자 화면은 미팅을 가로질러 보지만
LEP 의 사건은 그러지 않는다 — 여기서 열어 두면 `021` 에서 미팅을 좁힌 의미가 사라진다.
사건을 **여는 것 자체도** `access_log` 에 남는다.

### 4) 지우는 일은 사람이 정한다 (`022`)

`purge_candidates` 뷰는 **보여 주기만** 한다. `v2.purge_matter()` 는 **불러야만** 지운다 —
예약도 트리거도 배치도 걸지 않았다. `access_log` 는 파기해도 남는다:
파기했다는 사실 자체가 기록이어야 한다.

| 주소 | 무엇 |
|---|---|
| `/matters` | 사건 목록. 새 사건을 만들기 **전에** 이해충돌을 본다 — **막지 않고 보여 준다** |
| `/matters/:id` | 순서가 **사건의 단계에 따라 바뀐다**. 상담·기한이 둘 다 없으면 「사건 조사를 시작하십시오」 가 맨 위 — 상담이 요건의 상류다. 그 외에는 **기한 → 상담 → 요건 → 시계열 → 증거**. 지난 기한도 지우지 않는다 |
| `/deadlines` | **기한 대시보드.** 사건을 가로질러 급한 순서로. 지난 기한을 감추지 않는다 |

**추정 기한에는 `추정 — 확인 필요` 가 붙는다.** AI 가 뽑은 것과 사람이 넣은 것이
같은 모양이면 그 화면은 믿을 수 없다.

## 녹음이 도는 길 (2026-08-20 구간 녹음으로 바뀜)

```
녹음 중 · 10분마다 구간 하나 → POST /recordings   ← 회의가 끝나기를 기다리지 않는다
  │
  ├─ R2 저장                    ← File 을 그대로 넘긴다 (사본을 만들면 128MB 한도에 걸린다)
  ├─ DB insert (status=pending) ← 여기까지가 위험 구간, 실측 148ms
  └─ TranscribeWorkflow 기동    ← 응답은 여기서 끝난다 (577ms)
       │
       └─ 잠금 → STT → 화자 역할 → 저장 (status=done)

분석 시작 → POST /meetings/:id/analyze
  └─ AnalysisWorkflow
       전사 확인(최대 200초 대기) → 전사 → 화자 → 분석 → 리포트 → 완료
```

**예전에는 업로드 요청 안에서 전사를 기다렸다.** 10분 파일에 188초가 걸렸고,
그 대부분이 "파일은 R2 에 있고 DB 행은 없는" 구간이었다 —
잃은 줄 알았던 녹음 4개(40분 15초)가 거기서 생겼다.

**그리고 2026-08-20 에 회의 내내 하나로 받아 두던 것을 10분 구간으로 쪼갰다.**
83분 녹음을 통째로 잃고서다 — `완료` 뒤에 파일 전체를 `decodeAudioData` 로 펴는 구조였고
83분이면 약 1.9GB 라 아이폰 탭이 죽었다. 죽는 순간 **서버에는 아무것도 없었다.**

| | 전 | 후 |
|---|---|---|
| 서버에 처음 닿는 시점 | `완료` 를 누른 뒤 | **녹음 10분** |
| 83분 회의의 최대 유실 | **83분 전부** | 마지막 10분 |
| 브라우저가 한 번에 펴는 크기 | 길이에 비례 | **없음** — 구간을 그대로 올린다 |

구간은 `meeting_id` 없이 먼저 쌓이고 미팅을 만들 때 붙는다. **붙지 않은 것도 화면에 보여 준다** —
안전망이 잡아 놓고 손이 닿지 않으면 없는 것과 같다. 조사 기록은
`docs/2026-08-20-recording-lost-83min.md`.

## 배포 — 워크플로 하나 (2026-08-14 부터)

```bash
gh workflow run DB --repo MacTechIN/SEP-V2.0 -f action=migrate -f file=0NN_….sql  # 있으면 먼저
gh workflow run "Deploy" --repo MacTechIN/SEP-V2.0
```

타입 검사 → `build:prod` → **Worker** → 웹 → **번들 대조** → 태그.

**Worker 를 먼저 올린다.** 화면이 새 API 를 부르는데 API 가 옛것이면 그 사이가 고장이다.
반대 순서는 기능이 1분 늦게 오는 것뿐이다. `013` 이 그 경우였다 — 마이그레이션은
적용됐는데 Worker 가 옛 빌드라 로그인이 여전히 무제한이었다.

**마지막 대조가 핵심이다.** 배포 명령의 성공은 "요청이 받아들여졌다" 는 뜻이지
그 번들이 서비스된다는 뜻이 아니다. 그 둘을 같다고 본 것이 2026-08-12 에 `tsc` 가
깨진 채 하루 동안 프런트가 안 올라간 것을 아무도 모른 원인이다. 살아 있는 사이트가
방금 빌드한 번들을 줄 때까지 확인하고, 5분 안에 안 맞으면 실패한다.
태그는 그 확인이 끝난 뒤에 붙는다 — 안 올라간 것을 릴리스로 표시하지 않는다.

`npm run build` 는 localhost 를 가리키는 번들을 만든다. 반드시 `build:prod` (워크플로가 그렇게 한다).

**세 `package.json` 의 버전은 같은 번호로 함께 움직인다** (한 제품의 세 조각이다).

## 실시간 코칭의 판단 원칙

> 이 절은 구조가 아니라 **판단**을 적는다. 사고를 밟으며 하나씩 정해 온 것들이고
> 그전에는 코드 주석으로만 흩어져 있었다. **흩어진 판단은 자산이 아니다.**
> (2026-08-24 에 `docs/archive/2026-08-24-live-coaching-knowhow.md` 에서 옮겨 왔다)

### 축 — 경보의 비용은 방향에 따라 다르다

**이것은 회의가 끝난 뒤 읽는 리포트가 아니라, 고객 앞에서 말하는 중에 뜨는 경보다.**

여기서 나머지가 따라 나온다. 사후 분석은 틀려도 나중에 고쳐 읽으면 된다.
실시간은 **틀린 순간 그 회의가 흔들린다.** 그래서 정확도를 최대화하지 않고
**틀렸을 때의 피해가 작은 쪽으로 기울인다.**

| | 틀렸을 때 잃는 것 | 그래서 |
|---|---|---|
| 위험 오탐 | 고객 앞에서 화면이 빨개져 **영업담당의 말이 그 자리에서 흔들린다** | 연속 2회여야 승격 |
| 기회 놓침 | **그 기회 하나** | 즉시 알림 |

비대칭이 요점이다. 대칭으로 만들면 둘 중 한쪽이 반드시 잘못된 대가를 치른다.
규칙은 **서버 한 곳**에 있다(`services/risk.ts` `applyHysteresis`) — 화면에 두면
기록되는 `level_shown` 을 서버가 알 수 없고 화면이 늘면 각자 다르게 구현된다.

프롬프트도 같은 방향으로 기울어 있다 — `애매하면 normal. 과잉 경보 금지.`
일반적인 분류는 정확도를 요구하지만 우리는 **조용함**을 요구한다.

**너무 자주 외치는 경보는 꺼지지 않는 경보와 같다.** 2026-08-24 에 전사 품질 경고가
정상인 구간에 대고 고장이라고 외친 일을 겪고 규칙으로 세웠다. 등급을 늘리거나 임계값을
낮추자는 제안은 이 원칙과 먼저 겨뤄야 한다.

### 내보이는 방식 — 진단이 아니라 대사를 준다

판정을 셋으로 쪼개 낸다.

| 조각 | 무엇 |
|---|---|
| `reason` | 왜 그렇게 봤나 |
| `script` | **지금 이렇게 말하세요** — 읽고 그대로 옮길 문장 |
| `action` | 어떤 태도로 (경청·공감 / 근거 제시 / 클로징 …) |

**`script` 가 이 제품의 값이다.** 회의 중에 "고객이 망설입니다" 를 읽어도 할 수 있는 것이 없다.
3초 안에 읽고 입으로 옮길 수 있어야 쓸모가 있다.

등급이 `normal` 이어도 카드는 남긴다 — **꺼진 것과 조용한 것을 구분해 주기 위해서다.**
카드가 사라지면 사용자는 기능이 죽었는지 조용한 것인지 몰라 회의 중에 신경을 쓰게 된다.

피드백은 `도움됐어요 / 빗나갔어요` **둘뿐이다.** 회의 중이라서 그렇다 —
선택지가 셋 이상이면 아무도 안 누르고, 안 누르면 정답표가 안 생긴다.

### 구조 — 코칭은 녹음을 절대 건드리지 않는다

같은 마이크 스트림을 **두 번째 `MediaRecorder`** 가 읽는다. 코칭이 죽어도, 소켓이 끊겨도,
서버가 500 을 줘도 **녹음은 그대로 돈다.**

취향이 아니라 **83분을 잃은 뒤에 세운 규칙**이다. 회의는 다시 할 수 없고 코칭은 다시 볼 수 있다.
둘의 등급이 다르다. 신호 계산이 무거워져도 녹음 경로에 들어가지 않는다.

주기는 **꼬리물기**다 — 25초마다 부르는 것이 아니라 응답을 받은 뒤에 다음 주기를 건다.
서버가 느리면 주기가 저절로 늘어나 요청이 겹쳐 쌓이지 않는다. 별도의 큐도 상한도 필요 없다.
`setInterval` 로 짜면 느린 응답이 누적돼 회의 후반에 밀린다.

껐다 켜거나 일시정지·재개할 때 이전 주기가 나중에 깨어나 **루프가 둘이 되는 사고**가 실제로 났다.
`riskGenRef` 로 세대를 매겨 자기 세대가 아니면 조용히 끝낸다 —
**비용 사고는 이런 자리에서 난다. 기능은 정상으로 보이고 청구서만 두 배가 된다.**
꺼진 뒤에 도착한 판정도 버린다. **끈 뒤에 뜨는 코칭은 없는 것보다 나쁘다.**

### 자료 — 남이 갖기 어려운 것

`coaching_events` 에 **모델이 준 등급과 사람이 본 등급이 따로** 남고, 거기에
`도움됐어요/빗나갔어요` 가 붙는다(2026-08-24부터).

모델 API 를 쓰는 것은 누구나 한다. **한국어 영업 현장에서 사람이 맞다/틀리다를 표시한 자료**는
그 현장에 있는 쪽만 모을 수 있다. 오디오는 남기지 않는다 — 개선에 필요한 정보는
전사문과 계산된 숫자에 이미 들어 있고, 그 아쉬움과 유출 위험을 견주어 후자를 택했다.

**판단이 프롬프트에만 있으면 모델을 바꿀 때 함께 사라진다.** 비대칭은 이미 서버 코드로 옮겼고,
나머지도 규칙+LLM 합의를 만들 때 같은 자리로 옮긴다
(계획: `docs/2026-08-24-live-coaching-algorithm-plan.md`).
