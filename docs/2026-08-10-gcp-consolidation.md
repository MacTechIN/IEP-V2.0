# GCP 로 통합하는 안 — 조사

- 작성일: 2026-08-10
- 질문: 지금 흩어져 있는 DB·R2·Workers·Durable Objects·Pages 를 **GCP 안으로 통일**할 수 있는가
- 답: **기술적으로 전부 가능하다.** 다만 하나가 더 쉬워지고, 하나가 더 어려워지고, 비용은 오른다

---

## 1. 무엇이 무엇으로 가는가

| 지금 | GCP 대응 | 난이도 |
|---|---|---|
| Neon Postgres | **Cloud SQL for PostgreSQL** | 낮음 — 같은 Postgres. 덤프·복원 |
| R2 | **Cloud Storage (GCS)** | 낮음 — 객체 63MB, 키 규칙 그대로 |
| Workers (Hono API) | **Cloud Run** | 중간 — §3 참고 |
| Cloudflare Workflows | **Cloud Tasks** 또는 **Cloud Workflows** | 중간 — 내구 실행 모델이 다르다 |
| Durable Objects (스트림) | **Cloud Run (WebSocket)** | **낮음 — 오히려 쉬워진다** |
| Pages | **Firebase Hosting** 또는 GCS+Cloud CDN | 낮음 |
| Hyperdrive | 불필요 — Cloud Run 이 Cloud SQL 커넥터로 직접 붙는다 | — |

**이미 GCP 프로젝트가 있다**(STT 백업용). 그 위에 얹는 형태다.

---

## 2. 오히려 쉬워지는 것 — 실시간 스트림

지금 스트림 게이트웨이가 Durable Object 인 이유는 **Workers 에 연결을 듣는 소켓이 없어서**다.
그 제약 때문에 오늘 세 가지 결함을 연달아 밟았다 — `wss://` 스킴 거부, 101 반환 후 DO 정리,
이진 프레임의 Blob 문자열화.

**Cloud Run 은 WebSocket 을 그대로 지원한다**(요청 타임아웃 최대 60분).
`ws` 패키지가 있는 사내 원본 코드가 **거의 그대로 돈다.** DO 도, `WebSocketPair` 도,
`waitUntil` 로 수명을 붙잡는 기교도 필요 없다.

---

## 3. 짚고 넘어가야 할 사실

**Cloud Run 이 목적지라면, 사내 Express 백엔드를 거의 그대로 올릴 수 있었다.**

Worker 로의 이관(2,784줄)이 필요했던 이유는 Workers 가 Node 서버를 못 돌리기 때문이다.
Cloud Run 은 컨테이너를 돌리므로 그 제약이 없다. `docker-compose.prod.yml` 의 백엔드 이미지를
그대로 밀어 넣으면 된다.

그렇다고 지난 이관이 헛일은 아니다. 그 과정에서 찾아 고친 것들은 **Express 쪽에도 같이 반영했다** —
고객·미팅 IDOR, 계정 열거, 액션 범위 누락, 로그아웃 미작동, N+1, 난수 진행률, 실패 원인 미기록.
다만 **"Worker 로 옮기는 작업" 자체는 GCP 로 가면 버려진다.**

---

## 4. 더 어려워지는 것 — 분석 파이프라인

Cloudflare Workflows 는 **단계별 내구 실행**을 그대로 준다. 5단계에서 죽으면 STT 를 다시 하지 않는다.
GCP 에는 같은 모양이 없고 두 갈래다.

| 방식 | 성격 |
|---|---|
| **Cloud Run + Cloud Tasks** | 단계마다 태스크를 큐에 넣는다. 재시도는 태스크 단위. 상태는 우리가 DB 에 들고 있어야 한다 |
| **Cloud Workflows** | 오케스트레이션 전용 서비스. YAML 로 단계를 기술. Workflows 에 가장 가깝다 |
| Cloud Run 장시간 요청 | 60분 안에 끝난다면 그냥 한 요청으로. **가장 단순하지만 내구성이 없다** — 인스턴스가 죽으면 사라진다 |

우리는 이미 `analysis_stage`·`analysis_error` 컬럼으로 상태를 DB 에 들고 있으므로,
Cloud Tasks 방식이 무리는 아니다. 다만 **지금 공짜로 얻고 있는 것을 직접 만들어야 한다.**

---

## 5. 비용 — 오른다

지금은 실질 $0 이다(OpenAI·Deepgram 제외). 전부 무료 한도의 1% 미만이다.

| 항목 | Cloudflare 지금 | GCP 예상 |
|---|---|---|
| DB | Neon 무료 (32MB) | **Cloud SQL 최소 인스턴스 월 $10~30** — 의미 있는 무료 한도가 없다 |
| 객체 저장 | R2 무료 (63MB / 10GB) | GCS 5GB 무료 후 GB당 과금 |
| **송신(egress)** | **무료** | **GB당 과금** — 분석마다 오디오를 읽으므로 여기가 쌓인다 |
| API 실행 | Workers 무료 | Cloud Run 무료 한도 넉넉 |
| 정적 호스팅 | Pages 무료 | Firebase Hosting 무료 한도 있음 |

**가장 큰 차이는 Cloud SQL 과 egress 다.** R2 를 고른 이유 중 하나가 송신 무료였는데,
분석할 때마다 오디오를 읽는 이 앱에서는 그게 실제로 의미가 있다.

지금 규모(사용자 3명, 63MB)에서 **월 $0 → 월 $15~40 정도**를 예상한다.

---

## 6. 통합해서 얻는 것

비용이 오르는데도 고려할 만한 이유는 있다.

- **벤더가 하나로 줄어든다.** 지금은 Cloudflare + Neon + OpenAI + Deepgram + (곧) GCP 다.
  청구서·키·장애 지점·권한 관리가 다섯 갈래다
- **STT 백업이 자연스러워진다.** Google STT 를 이미 쓰기로 했으니 같은 프로젝트 안에 있는 편이 낫다.
  지금은 서비스 계정 JSON 을 Cloudflare 시크릿에 넣는 형태인데, Cloud Run 이면 **키 파일 없이**
  워크로드 아이덴티티로 붙는다 — **키를 만들고 보관하는 일 자체가 사라진다**
- **gRPC 를 쓸 수 있다.** Google STT 의 진짜 스트리밍(`StreamingRecognize`)이 열린다.
  지금 백업이 10초 버퍼 REST 인 이유가 Workers 가 gRPC 를 못 해서다
- 사내 서버를 내린 뒤에도 **컨테이너 기반**이라 로컬에서 같은 것을 돌려볼 수 있다

---

## 7. 옮긴다면 순서

C-0 이 그랬듯 **저장소부터, 앱은 나중에.** 각 단계가 되돌릴 수 있어야 한다.

| 단계 | 내용 | 되돌리기 |
|---|---|---|
| G-1 | Cloud SQL 생성 → Neon 덤프·복원 → 행 수 대조 | 연결 문자열 한 줄 |
| G-2 | GCS 버킷 → R2 객체 복사 → md5 대조 (원본 유지) | 아무것도 안 바뀜 |
| G-3 | Express 백엔드를 Cloud Run 에 배포 (이미지 그대로) | 트래픽을 안 보내면 됨 |
| G-4 | 프런트엔드 `VITE_API_URL` 을 Cloud Run 으로 → Firebase Hosting 배포 | 이전 Pages 배포로 롤백 |
| G-5 | 분석을 Cloud Tasks 로. 스트림을 Cloud Run WebSocket 으로 | 경로별 전환 |
| G-6 | Cloudflare 리소스 정리 | — |

**G-3 이 핵심이다.** 사내 Express 이미지를 그대로 쓰면 Worker 재이식이 필요 없다.
단, 오늘 Worker 에만 들어간 것들(Workflow 기반 분석, R2 접근, 실제 계산 대시보드, 비밀번호 변경)은
Express 로 역이식해야 한다 — **약 800줄 규모**로 추정한다.

---

## 8. 솔직한 권고

**지금 당장 옮기는 것은 권하지 않는다.** 이유는 셋이다.

**하나.** 오늘 옮긴 것이 어제 일이다. 방금 안정화된 것을 다시 흔드는 값이 크다.
지금 상태는 전 경로가 검증돼 있다 — 로그인·미팅·분석·업로드·실시간 전사까지.

**둘.** 비용이 오른다. 월 $0 에서 $15~40 은 절대액으로는 작지만, **얻는 것이 벤더 통합뿐**이다.
성능도 기능도 나아지지 않는다(스트림 구현이 단순해지는 것을 빼면).

**셋.** 지금 아픈 곳이 GCP 로 해결되지 않는다. 남은 과제는 Deepgram 비용, 23분 초과 미팅,
지어낸 수치 정리, 사내 서버 정리다. 어느 것도 플랫폼 문제가 아니다.

### 그럼에도 옮길 만한 때

- **사용자가 늘어 Neon 무료 한도를 넘길 때** — 어차피 유료가 되면 Cloud SQL 과 격차가 준다
- **Google STT 를 주경로로 쓰기로 할 때** — 그러면 gRPC 스트리밍이 필요하고, 그건 Workers 에서 안 된다
- **사내 서버를 완전히 접고 컨테이너 기반으로 통일하고 싶을 때**

### 지금 할 수 있는 절충

전부 옮기지 않고 **하나만** 옮기는 것도 된다. 예를 들어 **실시간 스트림만 Cloud Run 으로** 빼면,
오늘 겪은 DO 제약이 사라지고 Google STT 스트리밍(gRPC)도 열린다.
나머지는 Cloudflare 에 그대로 둔다. 벤더는 늘지만 아픈 곳 하나가 확실히 낫는다.
