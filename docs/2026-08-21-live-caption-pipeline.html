실시간 자막은 어디로 흐르고
어디서 끝나는가

마이크 하나에서 두 갈래가 나간다. 한쪽은 화면에 자막을 띄우고 사라지고, 다른 쪽은 파일로 저장돼 미팅노트가 된다. 두 경로는 서로 만나지 않는다.

전체 경로

같은 MediaStream 을 둘이 읽는다. 위 갈래가 실시간 자막, 아래 갈래가 녹음 저장이다.

한 프레임의 여정

100밀리초어치 소리 하나가 화면에 글자로 뜨기까지. 순서가 정보인 유일한 대목이라 번호를 붙인다.

  1. 워클릿이 128프레임씩 받는다그대로 보내면 초당 375번 전송이다. 1,600샘플(100ms)을 모아 한 번에 넘긴다.
  2. Float32 를 Int16 으로 자른다클리핑을 안 하면 큰 소리에서 값이 뒤집힌다. 결과가 3,200바이트 — 초당 32,000바이트다.
  3. WebSocket 이 이진 프레임으로 보낸다토큰은 쿼리스트링에 실린다. 브라우저 WebSocket 은 헤더를 붙일 수 없다.
  4. 게이트웨이가 관문 셋을 통과시킨다경로 · Origin 허용 목록 · JWT. Worker 와 같은 비밀키를 쓴다 — 한쪽에서 로그인하고 이쪽으로 붙는다.
  5. STT 엔진으로 그대로 중계된다게이트웨이는 저장하지 않는다. 흘려보내고 결과를 되돌릴 뿐이다.
  6. 중간 결과가 먼저, 확정이 나중에화면은 임시 결과를 맨 끝 한 줄만 유지한다. 쌓아 두면 같은 말이 여러 번 보인다.

엔진은 어떻게 골라지는가

주경로는 Deepgram 이다. 넘어가는 조건이 좁다 — 연결이 열리기 전에 실패했을 때만이다.

5분 벽과 스트림 회전

Google 의 스트리밍 인식은 약 305초에서 끊긴다. 5분 넘는 회의가 백업의 존재 이유라 그냥 둘 수 없다.

이 경로가 하지 않는 일

자막은 저장되지 않는다. 화면에 뜬 글자는 서버에도 DB 에도 남지 않는다. 코드에 finalText() 라는 함수가 있지만 아무도 부르지 않는다 — 붙여 넣을 곳이 없다.

게이트웨이는 오디오를 보관하지 않는다. 흘려보내고 결과를 되돌릴 뿐이다. 실시간 코칭 클립도 같다 — 전사한 뒤 곧바로 버린다.

기본값은 꺼짐이다. 스트리밍 전사는 분당 과금이라, 켠 사람에게만 돈다.

그래서 회의가 끝난 뒤 남는 녹취는 전부 아래 갈래에서 나온다. 자막이 좋아 보였는데 미팅노트가 다르다면, 둘이 서로 다른 엔진의 결과이기 때문이다.

자막 한 줄이 뜨는 데 관여하는 것만. 과금 방식 기준이다.
