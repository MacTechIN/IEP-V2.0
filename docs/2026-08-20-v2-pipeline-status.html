끝나고 한 번에 → 회의 중에 계속

예전에는 회의 내내 MediaRecorder 하나로 받아 두고 완료 를 누른 뒤에야 통째로 변환해 올렸다. 그 변환이 파일 전체를 펴는 방식이라 길이에 비례해 메모리를 먹었고, 83분에서 약 1.9GB 가 되어 아이폰 탭을 죽였다. 죽는 순간 서버에는 아무것도 없었다.

오늘 오전

무엇이 언제 끊겼나

Worker 요청 통계와 Cloud Run 로그를 겹쳐 보면 시각이 정확히 맞는다. 25초마다 도는 실시간 코칭이 회의가 살아 있다는 심장 박동 노릇을 했다 — 그것이 멈춘 자리가 곧 화면이 죽은 자리다.

안전망은 처음부터 없었다. 아이폰 사파리의 보관함을 열어 보니 조각이 0개였다. 83분이면 15초마다 약 330조각이 쌓였어야 하고 커밋된 쓰기는 탭이 죽어도 남는다. iOS 가 MediaRecorder.start(timeslice) 의 인자를 무시해 stop() 때 한 번만 데이터를 주는 것으로 보인다 — 그러면 중간 저장이 생길 수가 없다. 같은 날 2초짜리가 정상 업로드된 것과도 어긋나지 않는다. 짧은 녹음에서는 드러나지 않는 결함이다.

아직 손대지 않은 것

  • 확인 필요 새 구간 녹음이 기기에서 한 번도 돌지 않았다 다음 회의 전에 사파리를 완전히 닫았다 열어 새 번들을 받아야 한다. 녹음 화면의 “서버에 N구간 저장됨” 이 10분마다 올라가면 확인된 것이다.
  • 위험 R2 오프사이트 백업이 8/19부터 매 회차 실패 6시간마다 도는데 전부 실패한다. CLOUDFLARE_API_TOKEN 이 Object 범위라 R2 REST API 가 받지 않는다 — Admin Read & Write 로 바꿔야 한다. 그동안 올라온 녹음에는 사본이 없다.
  • 주의 화자 번호가 구간마다 새로 매겨진다 오늘 48분 5구간이 화자 12명으로 갈렸다. 구간을 짧게 할수록 심해지므로 10분보다 더 줄이기 어렵다. 구간 사이에 화자를 이어 붙이는 일이 따로 필요하다.
  • 주의 첫 10분은 여전히 서버에 아무것도 없다 그 사이에 탭이 죽으면 그만큼은 잃는다. iOS 에서는 기기 백업도 돌지 않으므로 완충이 없다. 줄이려면 위의 화자 문제와 맞바꿔야 한다.
  • 주의 Workers 로그를 나중에 볼 수 없다 [observability] 는 켜져 있으나 API 토큰에 조회 권한이 없어 오늘 조사에서 10000 Authentication error 로 막혔다. 권한만 더하면 다음부터는 rid 로 요청 하나를 통째로 따라갈 수 있다.
  • 낮음 sort_order 가 draft 개수로 정해진다 업로드가 큐 하나로 직렬이라 지금은 안전하다. 다만 녹음 도중에 draft 를 지우면 번호가 겹칠 수 있다. 남아 있는 낡은 draft 8건도 함께 정리할 값어치가 있다.
