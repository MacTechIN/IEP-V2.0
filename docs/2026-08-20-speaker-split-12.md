## ③ 파트 3 은 화자 분리 자체가 실패했다

620초·4,485자인데 **세그먼트가 1개다.**

`gpt-4o-transcribe-diarize` 가 거절돼 `whisper-1` 로 떨어졌고, 폴백에는 화자 정보가 없어
전체가 한 덩어리가 된다. 화자가 하나뿐이라 `mapSpeakerRoles` 의 1명 분기를 탄다.

```ts
if (speakers.length <= 1) return { [speakers[0] ?? 'A']: '영업대표' }
```

화면의 `영업대표 1` 이 이것이다.

### 원인 — 길이는 아니다

조각이 720초 상한을 넘어 거절된 것 아닌가 하는 가설이 있었다.
**클라이언트 보고값을 믿지 않고 R2 객체의 실제 바이트로 검산해 기각했다**
(16kHz 모노 16bit WAV → `(size - 44) / 32000`).

```
파트 1/5   19,563,614 B → 611.4초   (보고값 611)
파트 2/5   19,562,926 B → 611.3초   (보고값 611)
파트 3/5   19,851,542 B → 620.4초   (보고값 620)   ← 폴백이 난 조각
파트 4/5   17,810,468 B → 556.6초   (보고값 557)
파트 5/5   15,904,332 B → 497.0초   (보고값 497)
```

파트3 은 620.4초·19.85MB 로 **720초·25MB 양쪽 다 여유가 있다.**

### 진짜 원인 후보 — 재시도가 비대칭이다

```ts
let r = await call(known)
if (!r.ok && known.length > 0 && r.status >= 400 && r.status < 500) { r = await call([]) }
if (!r.ok) throw new Error(...)          // 5xx·네트워크는 여기서 곧장 포기
} catch { /* whisper 폴백 */ }
```

**4xx 는 다시 시도하는데 5xx·타임아웃은 한 번에 포기한다.**
한 겹 더 나쁘다 — `TranscribeWorkflow` 에 `retries: { limit: 2 }` 가 걸려 있지만
**whisper 폴백이 성공을 돌려주므로 워크플로가 재시도할 일이 없다고 판단한다.**
재시도 장치가 둘인데 둘 다 무력하다. 일시적 오류 한 번에 그 조각의 화자가 영구히 사라진다.

`rid` 로 Workers 로그를 보면 확정되는데, `CLOUDFLARE_API_TOKEN` 에 Observability 권한이
없어 `telemetry/query` 가 `10000 Authentication error` 로 막힌다.
(R2 백업이 8/15 부터 401 로 실패하는 것과 **같은 뿌리**다 — 토큰이 `Object` 범위로 좁혀져 있다.)

```
화자 A → 파트 [1, 2, 4, 5]      화자 E → 파트 [1, 2, 4]
화자 B → 파트 [1, 2, 4, 5]      화자 F → 파트 [1, 2, 4]
화자 C → 파트 [1, 2, 4, 5]      화자 G → 파트 [1, 2, 4]
화자 D → 파트 [1, 2, 4, 5]      화자 H → 파트 [1, 4]
```

STT 는 **파일 하나마다 독립적으로** A·B·C 를 붙인다. 파트1 의 `화자 A` 와 파트5 의
`화자 A` 는 아무 관계가 없다. 그런데 `workflows/analysis.ts` 가 이름표를 그대로 이어붙인다.

```ts
const r = source === 'recordings'
  ? Object.fromEntries(stt.segments.map((s) => [s.speaker, s.speaker]))   // 항등 사상
  : await AI.mapSpeakerRoles(env, stt.segments)
```

**`화자 A 267개` 는 서로 다른 최소 4명이 한 이름으로 뭉친 것이다.**

호출부(`services/recordings.ts:208`, `workflows/analysis.ts:168`)가 조각을 하나씩 따로
전사한다. **격리가 빠진 것이 아니라 애초에 이어 주는 것이 없다.**

## ⑤ 등록 목소리 매칭이 작동하지 않는다

`관리자` 로 붙은 발화 **전부**다.

```
파트1   32자   "but Oh, the insurance is like a"
파트4    5자   "Hmm."
파트4    3자   "So"
파트4    4자   "참조가"
파트4    5자   "안 돼."
```

**556개 중 5개, 합쳐서 49자.** 그중 셋이 영어 잡음이다.
파트 1·4 가 성공한 것이 아니라 **다섯 파트 전부 사실상 실패**했다.

### 갈린 원인 후보

```
클립이 2초짜리        → 기각. 실측 8,016ms (2026-08-12 등록, 자동 정지 8초를 채움)
파트별 4xx 거절       → 기각. 등록 클립은 다섯 파트에 동일하게 들어간다.
                        형식 거절이면 결정적이라 5회 전부 걸려야 한다
mime 에 codecs 파라미터 → 코드로 실재. 이 계정 값은 미확인
영어 오염             → 배포 후 재측정 필요
```

### `mime` 후보 — 코드 세 지점이 이어져 있다

```
frontend ProfilePage.tsx:71   const type = mr.mimeType || 'audio/webm'
worker   resources.ts:200     mime: audio.type || 'audio/webm'      ← 그대로 저장
worker   voice.ts:34          `data:${e.ref.mime};base64,${btoa(bin)}`
```

`mr.mimeType` 은 보통 `audio/webm;codecs=opus` 다. 그러면 data URL 이
`data:audio/webm;codecs=opus;base64,…` 가 된다. RFC 2397 상 문법 위반은 아니지만
파라미터가 끼면 거절하는 파서가 흔하다. **그러면 4xx 도 안 나고 실명만 안 붙는다** —
관측된 모양과 맞는다.

**고치는 자리는 서버 두 곳이다.** 클라이언트가 셋(v2 웹·V3 웹·앱)이라 클라이언트를
고치면 넷째가 또 만들고, 이미 저장된 행도 안 고쳐진다.

```ts
// 쓸 때 — routes/resources.ts. R2 contentType 도 같은 값으로
const mime = (audio.type || 'audio/webm').split(';')[0].trim()

// 읽을 때 — lib/voice.ts. ← 이쪽이 있어야 재등록 없이 옛 행이 살아난다
const base = (e.ref.mime || 'audio/webm').split(';')[0].trim()
```

확인하려면 `v2.users.voice_ref->>'mime'` 을 봐야 하는데,
`GET /users/me` 는 `duration_ms`·`enrolled_at` 만 돌려주고(저장 경로를 일부러 감춘다),
`gh workflow run DB` 는 `status|audit|migrate` 뿐이라 임의 쿼리가 안 된다.

## 관통하는 것 — 조용한 등급 강등

이 조사에서 나온 것들이 개별 버그가 아니라 **같은 모양**이다.

```
83분 녹음이 백업된 줄 알았는데  → IndexedDB 조각 0개            실제 발생
파트3 이 전사된 줄 알았는데     → 화자 없음                      실제 발생
목소리를 등록한 줄 알았는데     → 556개 중 5개·49자              실제 발생
미팅이 분석 완료로 찍혔는데     → 녹음 0건 · overall 70점        실제 발생
전사가 세 번 실패하면           → 영구히 전사 불가               잠복
```

전부 **성공 또는 정상으로 보고하고 실제로는 등급이 내려간 것**이다.
사용자는 결과가 나빠진 것만 보고 왜인지 모른다. **원인을 좁히기 어려운 이유 자체가 이 침묵이다.**

`toKnownSpeakers` 가 대표적이다 — R2 에서 클립이 사라져도, base64 가 깨져도, 형식이 틀려도
`[]` 를 돌려주고 전사는 평범하게 성공한다.

마지막 줄은 별도 결함이다 — `MAX_TRANSCRIBE_TRIES = 3` 인데 **`transcribe_tries` 를 0 으로
되돌리는 코드가 어디에도 없고**, `startTranscription` 은 `createDraft` 에서만 불려
사용자가 다시 시킬 경로가 없다. 지금 걸린 행은 없다(최근 20건 전부 `done`·`tries=1`).

## 조율

V3 세션 둘(`sep-v3-main-f0`·`sep-v3-main-f2`)과 조율했다. 화자 병합은 **아무도 착수하지 않았고**
착수 시 서로 먼저 알리기로 했다. 경계는 **v2 저장소는 v2 세션, V3 저장소는 V3 세션**,
같은 결함이 양쪽에 있으면 각자 자기 쪽을 고치고 서로 알린다.

V3 사본에도 같은 결함들이 있다(엔진이 사실상 같은 코드다). V3 `main` 은 origin 대비
16커밋 미푸시라 밖에서는 보이지 않는다 — `3026acf` 로 겪은 것과 같은 상황이다.
