# 서비스 점검 기록

한 시간에 한 번 `Health` 워크플로가 상태를 보고 여기 한 줄씩 남긴다.

```
2026-08-12 17:59  OK    web=70ms api=184ms stream=62ms login=1229ms db=ok
```

| 값 | 뜻 |
|---|---|
| `OK` | 전부 봤고 전부 정상 |
| `PART` | **일부를 못 봤다** — 아래 `못 봄:` 줄에 무엇을 왜 못 봤는지 적힌다 |
| `SLOW` | 살아 있으나 3초를 넘긴 항목이 있다 |
| `DOWN` | 실패한 항목이 있다 — 그 줄 아래에 무엇이 왜인지 적힌다 |

`PART` 를 `OK` 와 나눠 놓은 이유가 있다. 계정을 안 넣어 로그인을 건너뛰었는데
`login=ok` 로 적히면, **확인한 적 없는 것을 확인했다고 말하는 로그**가 된다.
감시가 거짓말을 하면 없느니만 못하다. 못 본 것은 `skip` 으로 적는다.

## 무엇을 보나

**살아 있는지만 보지 않는다.** HTTP 200 은 "죽지 않았다" 는 뜻일 뿐이다.

| 항목 | 확인 |
|---|---|
| `web` | 화면이 **번들 이름을 담은 index.html** 을 주는가 (오류 페이지를 200 으로 주는 경우를 잡는다) |
| `api` | Worker `/health` |
| `stream` | 실시간 자막 게이트웨이. Cloud Run 은 안 쓰면 0으로 내려가 첫 요청이 느린 것이 정상이다 |
| `auth` | 없는 계정으로 로그인해 **401 이 오는가** — 계정 없이 확인한다 |
| `db` | Neon 응답과 지연 |
| `transcribe` | **30분 넘게 밀린 전사가 있는가** — 쌓이면 Workflow 가 안 도는 것이다 |
| `analysis` | 24시간 미팅 수와 실패 수 (세기만 한다 — 무음 오디오도 실패로 잡힌다) |

### 인증은 왜 계정 없이 보나

없는 계정으로 로그인을 시도해서 401 이 오는지만 본다. 그것으로 **인증 라우트가 살아
있고, DB 까지 닿고, 거부가 동작한다**는 것이 확인된다 — 인증 사고의 대부분이 이 셋이다.
아무것도 만들지 않고 아무것도 바꾸지 않으며, 실패 로그인으로 잠기는 구조가 없는 것은
2026-08-15 에 확인했다.

`200` 이 오면 장애가 아니라 **사고**다. 아무 비밀번호나 통과한다는 뜻이다.

**확인되지 않는 것 하나**: 맞는 비밀번호로 토큰이 실제로 발급되는가.
JWT 서명 키가 잘못되면 이 검사는 통과하고 사용자는 못 들어온다.
그것까지 보려면 진짜 계정이 필요한데, 하루 24번 로그인할 전용 계정을 만들고
비밀번호를 CI 에 두는 값이 그 하나에 값하지 않는다고 판단했다.
필요해지면 `HEALTH_EMAIL`·`HEALTH_PASSWORD` 를 넣으면 그쪽으로 확인한다 — 코드는 그대로 있다.

## 커밋은 매시간 하지 않는다

하루 24개면 진짜 커밋이 그 아래 묻힌다. 남길 값어치가 있을 때만 남긴다:

- **실패했을 때** — 그 자체가 사건이다
- **실패에서 돌아왔을 때** — 언제 복구됐는지가 필요하다
- **6시간마다**(00·06·12·18 UTC) — 아무 일 없었다는 것도 기록이다

그 사이의 점검은 **Actions 실행 기록**에 남는다. 실패하면 워크플로가 실패로 끝나
GitHub 이 알림을 보낸다.

## 복구 훈련 (`restore-drill.log`)

`Restore drill` 워크플로를 손으로 돌린다. 프로덕션은 **읽기만** 하고(pg_dump),
복원은 러너 안의 일회용 Postgres 로 들어간다. 덤프는 밖으로 나가지 않고
건수·시간만 남는다.

**2026-08-18 에 다시 켰다.** (08-16 에 MVP 테스트가 끝나 껐던 것을 되살렸다.)
그 사이에 올라온 녹음은 사본이 없었다 — 훑기 방식이라 **다음 회차가 메운다.**

> 되살릴 때 토큰은 **`Admin Read & Write`** 여야 한다.
> `Object` 범위 토큰은 R2 REST API 가 받지 않는다 (2026-08-15 실측).
**Neon 의 시점 백업은 그대로 있다** — 없어지는 것은 백업이 아니라 *되돌릴 수 있다는 확인*이다.
두 번(08-13·08-14) 확인해 뒀고, 다시 필요하면 워크플로에 `schedule` 을 되살리면 된다.

**2026-08-13 첫 실행 — 복구됨.** 12개 테이블 2,461행이 건수와 **내용 해시까지**
전부 일치했다. 백업 19초(427KB), 복원 1초 미만.

`pg_restore` 가 0 으로 끝난 것을 근거로 삼지 않는다 — **테이블이 빈 채로 복원돼도
에러는 안 난다.** 그래서 원본과 복원본의 테이블별 건수와 내용 해시를 맞춘다.
하나라도 어긋나면 실패다.

여기서 나온 20초는 **데이터를 되돌리는 시간**이지 서비스가 돌아오는 시간이 아니다.
실제 사고에서는 Neon 브랜치를 새로 만들고 `DATABASE_URL` 을 바꿔 재배포하는 시간이
더 크다 — 그쪽은 아직 재 본 적이 없다.

## 녹음 백업 (`r2-backup.log`)

**2026-08-16 부로 예약 실행을 걷어냈다.** MVP 테스트가 끝나 하지 않기로 정했다.
**이미 넣은 사본은 그대로 있다** — 녹음 51개(511.7MB)가 백업 버킷에 있고 잠금이
2026-09-14 까지 삭제를 막는다. 없어지는 것은 새 녹음의 사본과 6시간마다 하던 확인이다.

다시 쓰려면 토큰을 `Admin Read & Write` 로 넣고 워크플로에 `schedule` 을 되살린다.
`Object` 범위 토큰은 이 REST API 가 받지 않는다 (2026-08-15 실측).

원래 이렇게 돌던 것이다 — R2 에는 버킷 간 복제도 버전관리도 없어서 만든 것이다.

**넣고 끝내지 않고, 넣은 것이 열리는지 그 자리에서 본다** (2026-08-15 에 녹음 훈련을
여기 합쳤다 — 두 워크플로가 같은 목록 대조를 두 번 하고 있었다):

1. 두 버킷 전체를 대조해 **없는 것만** 넣는다. 키에 업로드 시각을 붙여
   덮어쓰기가 나도 옛 판이 남는다
2. 원본마다 백업이 있고 **크기가 같은가** — 전부 본다. 잘린 사본이 여기서 잡힌다
3. 표본 3개를 **백업에서** 내려받아 `ffprobe` 로 연다 (최신·최대·최소를 섞는다)

**지우는 코드가 없다.** 삭제를 따라가면 백업이 아니라 복제고, 사고를 그대로 전파한다.

사본은 셋이다:

| | 어디 | 무엇을 막나 |
|---|---|---|
| 원본 | `sep-v2-uploads` | — |
| 백업 | 같은 계정 `sep-v2-uploads-backup` (30일 잠금) | 우리 코드·사람의 삭제, 덮어쓰기 |
| 계정 밖 | **다른 Cloudflare 계정** | 계정 정지·결제 실패·관리자 자격증명 유출 |

계정 밖 사본은 **원본에서 따로 읽는다.** 사본의 사본이면 백업 쪽 잘못을 물려받는다.
읽기와 쓰기의 자격증명이 갈라져 있어, 한쪽이 새도 다른 쪽 사본은 남는다.

DB 참조와의 대조는 여기서 하지 않는다 — `gh workflow run DB -f action=audit` 이 한다.
한 곳에 두면 올리다 만 옛 행 하나 때문에 백업이 매번 빨갛게 뜬다.

## 직접 돌리기

```bash
HEALTH_EMAIL=… HEALTH_PASSWORD=… DATABASE_URL=… node worker/tools/healthcheck.js
```

읽기만 한다. 아무것도 바꾸지 않는다.
