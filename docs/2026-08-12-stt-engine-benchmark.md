# 자막 엔진 실측 비교 — Deepgram 을 OpenAI 로 바꿀 것인가

- 측정일: 2026-08-12
- 질문: **실시간 자막을 OpenAI 로 옮기면 벤더가 하나 줄어드는데, 그럴 만한가**
- 답: **아니다.** 스트리밍 품질에서 절반을 잃는다.

---

## 왜 재봤나

지금 v2 는 벤더가 셋이다 — OpenAI(분석·코칭), Deepgram(자막), Google(자막 백업·중계 서버).
`docs/2026-08-10-gcp-consolidation.md` 에도 "남은 과제는 Deepgram 비용" 이라 적혀 있다.

그리고 **"OpenAI 로는 실시간이 안 된다" 는 사실이 아니다.** `whisper-1` 의 파일 엔드포인트로는
안 되지만, OpenAI 는 Realtime API 로 실시간 전사를 제공한다.
그러니 "왜 Deepgram 인가" 에 답하려면 재봐야 한다.

**저장소 어디에도 Deepgram 을 고른 근거가 없다.** 최초 커밋(`255c25a`, RT-1)에 비교 흔적이 없고,
그 결정은 기록되지 않았다. 그래서 지금 잰다.

---

## 어떻게 쟀나

- **오디오**: 회수한 실제 미팅 녹음(`~/recovered-recordings/`) 에서 60초 × 2구간
  - 샘플1 — `01_10m29s_00452368.wav` 의 120~180초
  - 샘플2 — `02_10m27s_22717a08.wav` 의 200~260초
- **스트리밍 경로**는 실시간 속도로 흘려보냈다(100ms 프레임). 파일 경로는 한 번에 보냈다.
- **Deepgram 은 프로덕션 게이트웨이를 통해** 쟀다. 키가 Secret Manager 에 있어 직접 못 부르는데,
  오히려 그편이 실제 경로라 정확하다.
- OpenAI 실시간은 GA API(`/v1/realtime?intent=transcription`, server VAD)를 썼다.
  **24kHz 이상만 받으므로 16kHz 원본을 업샘플했다** — 없던 정보가 생기지는 않지만
  이 점이 OpenAI 에 불리하게 작용했을 가능성은 남는다.

### 정확도를 어떻게 판정했나

사람이 검수한 정답이 없다. 그래서 **엔진 간 일치도**를 썼다 —
각 엔진의 결과를 정규화(한글·영숫자만 남김)한 뒤, 나머지 엔진들과 문자 단위로 얼마나 겹치는지 평균한 값이다.

**이건 절대 정확도가 아니다.** 다수가 틀리고 하나가 맞으면 그 하나가 낮게 나온다.
다만 여섯 엔진이 독립적으로 같은 문장을 내놓는다면 그게 정답에 가까울 확률이 높다.

## 읽어야 할 것

### 1. 결정적인 것은 정확도가 아니라 누락이다

스트리밍끼리 비교하면 **Deepgram 190자 vs OpenAI 실시간 95자.**
정확도가 조금 낮은 게 아니라 **내용의 절반이 안 나온다.** 두 샘플 모두에서 그랬다.

원인은 쓴 설정의 **서버 VAD** 로 보인다 — 발화 구간을 감지해 자르는데,
발화가 겹치고 배경음이 있는 미팅에서 많이 버린다.
`turn_detection` 을 끄려 했으나 `gpt-live-transcribe` 는
`Turn detection is not supported for this transcription model` 로 거절했다.

**그래서 "OpenAI 실시간이 나쁘다" 로 단정하지 않는다.** 다른 설정이면 나아질 수 있다.
확실한 것은 **기본 설정으로 바로 갈아탈 수 있는 상태가 아니라는 것**이다.

### 2. 요금은 이유가 되지 못한다

둘 다 분당 약 $0.006 로 사실상 같다. 옮겨서 아끼는 돈이 없다.

### 3. 화자 구분을 잃는다

Deepgram 은 `speaker` 를 준다. OpenAI 실시간은 주지 않는다.
지금 자막 화면이 "화자 1 / 화자 2" 를 보여주는 것이 그 값이다.

### 4. 파일 전사는 OpenAI 가 낫다

일치도 상위 셋이 전부 OpenAI 파일 모델이다. 이미 그렇게 쓰고 있다 —
코칭은 `whisper-1`, 본 분석은 `gpt-4o-transcribe-diarize`. 바꿀 이유가 없다.

한 가지 눈에 띄는 것: **`gpt-4o-mini-transcribe` 는 103자만 뽑는다**(다른 파일 모델의 절반).
코칭의 STT 를 mini 로 바꿔 비용을 절반으로 줄이자는 생각이 나올 수 있는데,
**내용도 절반이 된다.** 하지 말 것.

---

## 결론

**옮기지 않는다.** 얻는 것은 벤더 하나 감소뿐이고, 잃는 것은 자막 내용의 절반과 화자 구분이다.

### 다시 잴 시점

- OpenAI 실시간 전사에 **화자 구분**이 추가될 때
- **VAD 를 끄고 연속 전사**하는 옵션이 생길 때
- Deepgram 요금이 오르거나 서비스가 불안정해질 때

재현하려면 이 문서의 "어떻게 쟀나" 를 그대로 따르면 된다.
벤치 스크립트는 저장소에 남기지 않았다 — 일회성이고, 남기면 낡은 채로 굴러다닌다.
